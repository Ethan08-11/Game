# 沙箱支付接入方案（不新增数据库字段版）

> 目标：在不新增数据库字段的前提下，快速接入一个“沙箱支付”能力，优先满足开发联调、回调验证、前后端串联和后续可扩展性。

---

## 1. 现状判断

当前项目是一个 Spring Boot 后端，已经有这些比较适合承载支付能力的基础：

- 统一的 `Result<T>` 响应结构
- 现成的鉴权体系（`Authorization` + Access Token）
- `application.yml` / Nacos 配置体系
- Controller / Service / Mapper 分层清晰
- Redis、RabbitMQ、Feign 等基础设施已经具备

因此如果只是做一个“沙箱支付”，最省事的做法是：

- **不落库订单状态** 或只做最少的内存/缓存状态
- **先做一个标准支付接口和回调接口**
- **支付结果以回调或前端轮询为准**
- **通过配置文件切换沙箱/正式环境**

---

## 2. 推荐方案总览

### 方案 A：最轻量的“接口模拟型”沙箱支付

适合：

- 先把前后端流程跑通
- 暂时不接真实支付渠道
- 只需要演示“下单 -> 支付 -> 回调 -> 展示结果”

特点：

- 后端提供支付创建接口
- 后端返回一个沙箱支付跳转地址或模拟表单
- 前端跳转到沙箱页面完成支付
- 沙箱平台回调后端
- 后端返回支付结果给前端

优点：

- 改动小
- 不需要新增数据库字段
- 很适合联调和演示

缺点：

- 支付状态不持久化，重启后状态可能丢失
- 适合测试，不适合生产

---

### 方案 B：Redis 临时态支付

适合：

- 想要稍微稳一点
- 不想改数据库，但要保存支付状态、订单号、回调结果

特点：

- 订单信息写入 Redis，设置过期时间
- 支付创建后将状态放到 Redis
- 回调时更新 Redis 中的状态
- 前端通过查询接口查看支付结果

优点：

- 不改表结构
- 状态比纯内存稳定
- 适合短期测试

缺点：

- 仍然不是强持久化
- 需要额外维护 Redis key 设计

---

### 方案 C：完整支付适配器模式

适合：

- 后面可能要接微信支付、支付宝、第三方聚合支付
- 希望以后无痛切换渠道

特点：

- 抽象 `PaymentService` 接口
- `SandboxPaymentService` 实现沙箱支付
- 后续再加 `AlipayPaymentService`、`WeChatPaymentService`
- Controller 层不关心具体渠道

优点：

- 结构最好
- 后期扩展最方便

缺点：

- 初期代码稍多
- 需要先设计接口

---

## 3. 建议采用的落地方式

如果你的目标是“简单一点，不加数据库字段”，我建议：

> **方案 A + 方案 C 的轻量组合**

也就是：

- 后端先抽象一个 `PaymentService`
- 先只实现一个 `SandboxPaymentService`
- 通过配置决定是否启用沙箱
- 状态先用 Redis 或直接通过回调结果确认

这样既简单，又不至于把代码写死。

---

## 4. 后端需要新增哪些代码

下面按模块拆。

### 4.1 新增支付相关 Controller

建议新增一个独立包，例如：

- `cc.shturl.wa.demo.controller.PaymentController`

建议接口：

#### 1）创建支付单

`POST /api/payments/create`

请求示例：

```json
{
  "bizType": "RECHARGE",
  "bizId": "123456",
  "amount": 1000,
  "subject": "充值100元",
  "returnUrl": "https://frontend.xxx.com/pay/return",
  "notifyUrl": "https://backend.xxx.com/api/payments/notify"
}
```

返回示例：

```json
{
  "code": 0,
  "data": {
    "orderNo": "P202608020001",
    "payUrl": "https://sandbox-pay.xxx.com/pay?token=xxx",
    "qrCodeUrl": null,
    "expiredAt": "2026-08-02T10:30:00"
  }
}
```

#### 2）支付状态查询

`GET /api/payments/{orderNo}`

用途：

- 前端轮询订单状态
- 支付成功后刷新 UI

#### 3）支付回调

`POST /api/payments/notify`

用途：

- 沙箱支付平台主动通知后端
- 后端验签、更新状态、返回 `success`

#### 4）前端跳转回调页

`GET /api/payments/return`

用途：

- 用户支付完成后跳回前端
- 前端据此刷新订单状态

---

### 4.2 新增支付服务层

建议新增：

- `PaymentService`
- `SandboxPaymentServiceImpl`

接口建议：

```java
public interface PaymentService {
    PaymentCreateResp create(PaymentCreateReq request, Long userId);
    PaymentStatusResp query(String orderNo, Long userId);
    void notify(PaymentNotifyReq request);
    String buildPayUrl(String orderNo);
}
```

实现上，沙箱版可以先做成：

- 生成订单号
- 生成一个签名 token
- 组织支付 URL
- 校验回调签名
- 更新临时状态

---

### 4.3 新增 DTO

建议新增请求/响应 DTO：

#### 请求

- `PaymentCreateReq`
- `PaymentNotifyReq`
- `PaymentQueryReq`（可选）

#### 响应

- `PaymentCreateResp`
- `PaymentStatusResp`
- `PaymentReturnResp`（可选）

字段建议：

- `orderNo`
- `bizType`
- `bizId`
- `amount`
- `status`
- `payUrl`
- `expiredAt`
- `message`

---

### 4.4 新增枚举或常量类

建议新增：

- `PaymentStatus`
  - `CREATED`
  - `PAYING`
  - `SUCCESS`
  - `FAIL`
  - `CLOSED`
- `PaymentBizType`
  - `RECHARGE`
  - `VIP`
  - `ITEM`
  - `GAME_REWARD`

如果不想加枚举，也可以先用字符串常量。

---

### 4.5 新增配置类

建议新增：

- `PaymentProperties`

用于读取配置：

- 沙箱开关
- 支付商户号
- 支付密钥
- 沙箱地址
- 前端返回地址
- 回调地址
- 支付超时时间

---

### 4.6 可选：Redis 临时存储

如果你不想加数据库字段，但又想保存订单状态，建议用 Redis。

Key 设计示例：

- `payment:order:{orderNo}`
- `payment:notify:{orderNo}`
- `payment:user:{userId}:orders`

存储内容：

- 订单号
- 用户 ID
- 支付金额
- 业务类型
- 订单状态
- 创建时间
- 回调状态

TTL 建议：

- 30 分钟或 2 小时

这样就不用改数据库表结构。

## 5. 需要什么配置文件

### 5.1 `application.yml` 中新增配置

建议加一个 `payment` 段：

```yaml
payment:
  sandbox:
    enabled: true
    base-url: https://sandbox-pay.example.com
    merchant-id: ${PAY_MERCHANT_ID:demo-merchant}
    app-id: ${PAY_APP_ID:demo-app}
    secret: ${PAY_SECRET:demo-secret}
    notify-url: ${PAY_NOTIFY_URL:http://localhost:8080/api/payments/notify}
    return-url: ${PAY_RETURN_URL:http://localhost:5173/pay/return}
    timeout-minutes: 30
```

如果你希望把配置收敛到 Nacos，也可以直接放到 Nacos 的 `wa-demo-service.yml` 里。

---

### 5.2 `.env.example`

如果项目有本地环境变量文件，建议同步补充：

- `PAY_MERCHANT_ID`
- `PAY_APP_ID`
- `PAY_SECRET`
- `PAY_NOTIFY_URL`
- `PAY_RETURN_URL`

---

### 5.3 `Nacos` 配置

如果项目部署时依赖 Nacos，建议把支付配置也放进去，避免本地和线上配置不一致。

## 6. 后端最小实现方案

如果你想最简单地先跑起来，后端可以做成下面这个最小闭环：

### 6.1 创建订单时

1. 接收前端请求
2. 生成 `orderNo`
3. 将订单信息写入 Redis
4. 返回 `payUrl`

### 6.2 前端跳转到沙箱支付页

1. 用户完成支付
2. 沙箱平台调用 `notifyUrl`
3. 后端验签成功后，把 Redis 中订单状态改成 `SUCCESS`

### 6.3 前端查询状态

1. 前端轮询 `GET /api/payments/{orderNo}`
2. 如果状态变成 `SUCCESS`，页面提示支付完成

---

## 7. 前端需要怎么接支付接口

### 7.1 页面交互建议

前端可以拆成 3 步：

#### 第一步：点击支付按钮

调用后端：

`POST /api/payments/create`

拿到：

- `orderNo`
- `payUrl`

#### 第二步：跳转支付页面

前端用：

- `window.location.href = payUrl`
- 或者打开新窗口
- 或者嵌入 iframe / WebView（看沙箱能力）

#### 第三步：支付后回到前端

前端监听：

- `returnUrl`
- 或者回调页面路由
- 或者轮询订单状态

---

### 7.2 前端建议的接口封装

建议单独封一个 `paymentApi.ts`，里面至少有三个方法：

- `createPayment(data)`
- `getPaymentStatus(orderNo)`
- `handlePaymentReturn()`

---

### 7.3 前端状态机建议

前端页面状态可以简单分为：

- `idle`
- `creating`
- `paying`
- `polling`
- `success`
- `failed`

这样 UI 会更清晰。

---

## 8. 推荐的接口定义方式

### 请求创建支付

```http
POST /api/payments/create
Authorization: Bearer xxx
Content-Type: application/json
```

```json
{
  "bizType": "RECHARGE",
  "bizId": "ROOM_1001",
  "amount": 1000,
  "subject": "房间复活次数购买",
  "returnUrl": "http://localhost:5173/pay/result",
  "notifyUrl": "http://localhost:8080/api/payments/notify"
}
```

### 返回

```json
{
  "code": 0,
  "data": {
    "orderNo": "P202608020001",
    "payUrl": "https://sandbox-pay.example.com/pay?orderNo=P202608020001&token=xxx",
    "status": "CREATED"
  }
}
```

### 查询支付状态

```http
GET /api/payments/P202608020001
Authorization: Bearer xxx
```

### 回调

```http
POST /api/payments/notify
Content-Type: application/json
```

## 9. 安全和校验建议

即使是沙箱支付，也建议至少做这些：

- 回调签名校验
- 金额一致性校验
- 用户 ID 校验
- 订单号唯一性校验
- 防重复通知
- 超时订单自动关闭

如果不做这些，前后端联调虽然快，但后面很容易出问题。

## 10. 我建议你最终采用的落地版本

### 后端

- `PaymentController`
- `PaymentService`
- `SandboxPaymentServiceImpl`
- `PaymentProperties`
- `PaymentCreateReq/Resp`
- `PaymentNotifyReq`
- Redis 订单状态缓存

### 配置

- `application.yml` 增加 `payment.sandbox`
- `.env.example` 增加支付环境变量
- 如有 Nacos，同步补充远程配置

### 前端

- `paymentApi.ts`
- 支付按钮调用创建接口
- 跳转 `payUrl`
- 回跳后查询订单状态
- 支付成功后刷新业务页面

---

## 11. 最简实现清单

如果只做最小可用版本，建议先做这 6 件事：

1. 新增 `PaymentController`
2. 新增 `PaymentService` 和 `SandboxPaymentServiceImpl`
3. 新增 `PaymentCreateReq/Resp`、`PaymentNotifyReq`、`PaymentStatusResp`
4. 新增 `payment.sandbox` 配置
5. 用 Redis 保存订单临时状态
6. 前端实现“创建订单 -> 跳转支付 -> 回查状态”三步

---

## 12. 结论

如果你不想加数据库字段，沙箱支付最推荐的方式是：

- **订单状态用 Redis 或临时内存保存**
- **后端抽一个支付服务接口，先实现沙箱版**
- **前端按“创建订单 -> 跳转支付页 -> 查询状态”的标准流程接入**

这套方案改动小，联调快，也方便以后平滑替换成真实支付渠道。
