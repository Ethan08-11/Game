# 接口测试文档

## 1. 测试目标

本文档用于验证当前后端已实现的认证接口、用户接口、好友接口、任务接口、成就接口以及在线状态相关方案是否可正常使用，重点覆盖：

- 用户注册
- 用户登录
- Token 返回结构
- 基础参数校验
- 重复注册与错误登录的异常返回
- 用户在线状态的 Redis 方案
- 好友在线状态显示
- 掉线重连与会话失效策略
- 任务列表查询
- 成就列表查询
- 我的成就查询

## 2. 当前可测试接口

### 2.1 注册

- **Method**: `POST`
- **URL**: `/api/auth/register`
- **Content-Type**: `application/json`

#### 请求体

```json
{
  "username": "player_03",
  "password": "password123"
}
```

#### 成功响应示例

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "token": "access-token",
    "refreshToken": "refresh-token",
    "user": {
      "id": 3,
      "username": "player_03",
      "displayName": "player_03",
      "avatarUrl": null
    }
  }
}
```

#### 测试方法

1. 启动 MySQL、Redis、Nacos、RabbitMQ 和后端服务。
2. 用 Postman 或 Apifox 发起 `POST /api/auth/register`。
3. 检查返回的 `token`、`refreshToken`、`user.id` 是否存在。
4. 直接登录数据库，确认：
   - `users` 表新增一条记录
   - `user_profiles` 表自动新增一条记录
   - `password_hash` 不是明文
5. 再次使用同一用户名注册，确认返回“用户名已存在”。

### 2.7 查询广告复活状态

- **Method**: `GET`
- **URL**: `/api/matches/{matchId}/revive/status?userId={userId}`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 字段说明

- `matchId`：对局 ID。
- `userId`：当前查询的玩家 ID。
- `reviveEnabled`：是否开启广告复活功能。
- `canRevive`：当前玩家是否满足复活条件。
- `reviveCount`：当前玩家本局已复活次数。
- `reviveLimit`：当前玩家本局允许的最大复活次数，来源于 `match_players.revive_limit`。
- `currentHp`：当前玩家血量。
- `maxHp`：当前玩家最大血量。
- `remainingSeconds`：如果后端未来加入复活倒计时，这里返回剩余秒数；当前版本可为 `null`。
- `lastReviveAt`：最近一次复活时间；未复活时为 `null`。
- `reviveStatus`：复活状态值，当前约定为 `0` 不可复活、`1` 可复活/等待复活、`2` 已复活；
- `message`：状态提示文案；
- `canRevive` 只有在对局 `status=1`、玩家血量不高于 0 且复活次数未用尽时才为 `true`；进入 `REVIVE_WAIT` 后可发起复活，等待超时或对局结束后不可复活。

#### 成功响应示例

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "matchId": 60,
    "userId": 15,
    "reviveEnabled": true,
    "canRevive": true,
    "reviveCount": 0,
    "reviveLimit": 1,
    "currentHp": 0,
    "maxHp": 15,
    "remainingSeconds": null,
    "lastReviveAt": null,
    "reviveStatus": 1,
    "message": "可以观看广告复活"
  }
}
```

#### 测试方法

1. 先让某个玩家血量降到 0。
2. 调用该接口，确认返回 `canRevive=true`。
3. 检查 `reviveCount`、`reviveStatus` 是否符合当前状态。

### 2.8 提交广告复活请求

- **Method**: `POST`
- **URL**: `/api/matches/{matchId}/revive/request`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Content-Type**: `application/json`

#### 字段说明

- `userId`：申请复活的玩家 ID。
- `adRequestId`：广告请求唯一 ID，用于防重复提交和日志追踪。
- `adPlatform`：广告平台或来源，未填写时后端默认按 `manual` 处理。
- `reviveReason`：复活原因或备注。
- `adCallbackRaw`：广告回调原始内容，便于审计和排查。

#### 请求体

```json
{
  "userId": 15,
  "adRequestId": "ad-20260729-0001",
  "adPlatform": "manual",
  "reviveReason": "watch_ad",
  "adCallbackRaw": "{\"completed\":true}"
}
```

#### 字段说明

- `matchId`：对局 ID。
- `userId`：玩家 ID。
- `beforeHp`：复活前血量。
- `afterHp`：复活后实际血量；当前由后端在 `10~20` 中随机生成，并限制不超过玩家 `maxHp`；
- `reviveCount`：复活后本局已复活次数。
- `reviveLimit`：本局允许的最大复活次数，来源于 `match_players.revive_limit`。
- `reviveStatus`：复活状态值，当前约定为 `0` 不可复活、`1` 待复活/死亡、`2` 已复活。
- `currentRound`：当前回合号。
- `version`：对局版本号，用于前端同步。
- `revivedAt`：复活时间。
- `message`：结果提示文案。

#### 成功响应示例

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "matchId": 60,
    "userId": 15,
    "beforeHp": 0,
    "afterHp": 1,
    "reviveCount": 1,
    "reviveStatus": 2,
    "currentRound": 1,
    "version": 3,
    "revivedAt": "2026-07-29T18:30:00",
    "message": "复活成功"
  }
}
```

#### 测试方法

1. 确认玩家当前血量为 0。
2. 确认该局还允许复活。
3. 调用该接口，确认血量恢复为 1。
4. 检查数据库：
   - `match_players.current_hp` 变为 1
   - `match_players.revive_count` 自增
   - `match_players.revive_limit` 保持当前配置值
   - `match_players.last_revive_at` 被更新
   - `match_players.revive_status` 更新
   - `match_revive_logs` 新增一条日志
5. 检查 WebSocket 是否收到 `match.revive.success`。

## 3. 测试顺序建议

1. 调用注册接口创建新用户
2. 调用登录接口拿到 `accessToken` 和 `refreshToken`
3. 调用 `GET /api/auth/me` 验证登录态
4. 调用 `POST /api/auth/refresh` 验证刷新能力
5. 调用 `POST /api/auth/logout` 验证登出能力
6. 再次调用 `GET /api/auth/me`，确认 Token 已失效

## 4. 测试前准备

### 4.1 服务启动

确保以下服务已启动：

- 后端应用
- MySQL
- Redis
- Nacos（如果当前环境依赖远程配置）
- RabbitMQ（如果应用启动时启用了相关配置）

### 4.2 数据库准备

确认数据库中已经创建表结构，并且连接信息与 `application.yml` 一致。

### 4.3 Redis 准备

确认 Redis 中可以写入如下 Key：

- `auth:access:{token}`
- `auth:user:access:{userId}`
- `auth:refresh:{token}`
- `auth:user:refresh:{userId}`
- `auth:refresh:pair:{refreshToken}`
- `auth:user:session:{userId}`
- `online:user:{userId}`

#### Token 有效时长说明

当前项目不是纯 JWT，而是 Redis 会话令牌方案，因此 Token 由服务端控制生命周期：

- `accessToken` 默认 30 分钟
- `refreshToken` 默认 7 天

如果超过有效期：

- Redis 中对应 key 会自动过期删除
- 客户端再携带旧 token 调用接口会被判定为失效
- 需要重新登录，或在 refreshToken 仍有效时先刷新再继续使用

## 7. 好友接口测试

### 7.1 获取我的好友列表

- **Method**: `GET`
- **URL**: `/api/friends`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 说明

该接口现在按“双向好友”逻辑返回结果：

- 只要当前用户出现在好友关系记录的任意一侧，都会被返回
- 前端无需关心关系记录是 `user_id -> friend_id` 还是反向记录

#### 测试方法

1. 先准备一组好友关系数据。
2. 用登录后的 `accessToken` 调用接口。
3. 分别用关系双方账号登录，确认双方都能看到同一位好友。
4. 检查返回列表中是否包含：
   - `id`
   - `userId`
   - `friendId`
   - `status`
   - `remarkName`
   - `username`
   - `displayName`
   - `avatarUrl`
   - `onlineStatus`

### 7.2 发送好友申请

- **Method**: `POST`
- **URL**: `/api/friends/request`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Content-Type**: `application/json`

#### 请求体

```json
{
  "friendId": 9,
  "remarkName": "测试好友"
}
```

#### 测试方法

1. 使用当前账号登录。
2. 确认目标用户存在且不是自己。
3. 调用发送好友申请接口。
4. 检查数据库好友关系是否新增一条待处理记录。

### 7.3 接受好友申请

- **Method**: `PUT`
- **URL**: `/api/friends/{id}/accept`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Content-Type**: `application/json`

#### 请求体

```json
{
  "remarkName": "好朋友"
}
```

#### 说明

- 如果不传 `remarkName`，后端会自动默认填入申请发起方的用户名。
- 如果传了 `remarkName`，则以请求中的值为准。
- 这条备注会同步写入 `friend_remark` 表，作为当前登录用户视角下的好友备注。

#### 测试方法

1. 使用被邀请方账号登录。
2. 调用接受好友申请接口。
3. 检查好友关系状态是否变为已接受。
4. 检查 `remarkName` 是否按请求更新；如果未传，则应默认保存为申请发起方的用户名。
5. 检查 `friend_remark` 表是否新增或更新了当前用户对该好友的备注记录。
6. 再次调用好友列表接口，确认双方互相可见。

### 8.2 获取我的任务进度

- **Method**: `GET`
- **URL**: `/api/tasks/me`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 返回字段说明

- `id`：用户任务记录 ID；
- `taskId`：任务定义 ID；
- `taskCode`：任务编码；
- `taskName`：任务名称；
- `taskType`：任务类型，如 `daily` / `weekly` / `monthly`；
- `resetType`：任务重置类型，如 `DAILY` / `WEEKLY` / `MONTHLY`；
- `periodScope`：任务统计周期范围，如 `DAY` / `WEEK` / `MONTH`；
- `progressType`：任务进度类型，如 `WIN_COUNT` / `LOSE_COUNT` / `DISTINCT_TEAMMATE_COUNT`；
- `description`：任务描述；
- `conditionType`：任务条件类型；
- `conditionValue`：任务条件参数 JSON；
- `rewardType`：奖励类型，如 `money` / `exp` / `card`；
- `rewardValue`：奖励内容 JSON；
- `targetCount`：任务目标次数；
- `progressValue`：当前任务进度值；
- `status`：任务状态，`0` 未开始，`1` 进行中，`2` 已完成，`3` 已领取；
- `periodKey`：当前任务所属周期标识，例如 `2026-07-30`；
- `completedAt`：任务完成时间；
- `claimedAt`：任务奖励领取时间。

#### 测试方法

2. 检查是否返回当前用户的任务进度列表。

### 8.3 领取任务奖励

- **Method**: `POST`
- **URL**: `/api/tasks/{userTaskId}/claim`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 返回字段说明

- `userTaskId`：用户任务记录 ID；
- `taskId`：任务定义 ID；
- `progressValue`：当前任务进度值；
- `targetValue`：任务目标值；
- `status`：任务状态，`0` 未开始，`1` 进行中，`2` 已完成，`3` 已领取；

### 8.4 对局结束自动更新任务进度

### 11.9 已在房间或对局中的玩家不可重复组队

本次没有新增接口，而是在原有“发送邀请”和“接受邀请”接口中增加权威校验。

#### 发送邀请时校验

调用：

```text
POST /api/rooms/invites
```

后端会同时检查邀请人和被邀请人。如果任意一方存在 `left_at IS NULL` 且所属房间未关闭，并且房间状态为 `0/1/2`，请求会被拒绝：

- 房间状态为 `0` 或 `1`：提示“用户已在房间中”；
- 房间状态为 `2` 或已经绑定 `matchId`：提示“用户正在对局中”。

#### 接受邀请时再次校验

调用：

```text
POST /api/rooms/invites/{inviteId}/accept
```

即使邀请发送时双方都空闲，接受时仍会重新检查：

- 邀请是否超时；
- 双方是否仍为好友；
- 双方是否仍在线；
- 双方是否已经进入其他有效房间或正式对局。

接受邀请过程会对双方用户加分布式锁，避免同一个玩家并发接受两个邀请并被加入两个房间。

#### 测试一：邀请人已经在房间

1. 用户 3 和用户 9 先成功创建房间 A。
2. 保持房间 A 的 `status` 为 `0`、`1` 或 `2`，成员 `left_at` 为 `NULL`。
3. 用户 3 再邀请另一个在线好友。
4. 预期邀请请求失败，不产生新的 `room_invites` 记录，提示用户已在房间或正在对局。

#### 测试二：被邀请人已经在房间

1. 用户 9 已经在有效房间 A。
2. 另一个空闲好友尝试邀请用户 9。
3. 预期发送邀请失败，不产生新的邀请记录。

#### 测试三：发出邀请后玩家进入其他房间

1. 用户 A 向用户 B 发送邀请 X，此时双方空闲。
2. 用户 B 通过另一份邀请先进入房间 Y。
3. 用户 B 再接受邀请 X。
4. 预期接受失败，不创建第二个房间，邀请 X 不会变为已接受。

#### 测试四：并发接受两份邀请

1. 用户 B 同时持有用户 A 和用户 C 发出的两份待处理邀请。
2. 并发调用两份邀请的接受接口。
3. 预期最多只有一个请求成功。
4. 检查用户 B 在所有 `status IN (0,1,2)` 且未关闭的房间中最多只有一条有效成员关系。

#### 测试五：邀请超时后接受

1. 将待处理邀请的 `expired_at` 调整为当前时间之前。
2. 调用接受邀请接口。
3. 预期提示“邀请已超时”，不得创建房间。

#### 历史测试数据注意事项

空闲校验会把以下成员关系视为有效占用：

```text
room_members.left_at IS NULL
且 game_rooms.closed_at IS NULL
且 game_rooms.status IN (0, 1, 2)
```

如果旧测试房间已经废弃，应将房间更新为 `status=3` 并设置 `closed_at`，或为成员设置 `left_at`，否则旧数据会按设计阻止玩家再次组队。

## 14. 第一阶段正式对局接口

### 13.1 对局自动创建触发方式

正式对局没有单独的创建接口。双方分别调用房间准备接口后，当第二名玩家准备成功时，后端自动执行以下操作：

1. 校验房间中正好有两名玩家。
2. 校验两名玩家都已准备，并分别选择 `sales` 和 `purchase`。
3. 为房间创建唯一正式对局。
4. 随机固化本局顾客并选择启用的霸凌者。
5. 初始化销售部玩家 15 点血量、采购部玩家 20 点血量。
6. 初始化双方防御为 0、员工调用机会为 3。
7. 按 `deck_card_configs` 为双方各生成 20 张本局卡牌并洗牌。
8. 双方各抽取 5 张第一回合手牌。
9. 创建第一回合并将房间状态更新为对战中。

触发接口仍为：

- **Method**: `POST`
- **URL**: `/api/rooms/{roomId}/ready`
- **Headers**: `Authorization: Bearer {accessToken}`

第二名玩家准备成功后，响应中的房间数据应满足：

```json
{
  "status": 2,
  "matchId": 1
}
```

其中 `status=2` 表示房间已经进入对战中。

双方准备并完成数据库初始化后，两名玩家都会收到：

### 13.3 获取正式对局状态

- **Method**: `GET`
- **URL**: `/api/matches/{matchId}`
- **Headers**: `Authorization: Bearer {accessToken}`

#### `matches.phase` 说明

当前接口返回的 `phase` 是对局主阶段字段，实际可能出现以下值：

- `INITIALIZING`：对局初始化中；
- `SELECT_FIRST_PLAYER`：等待选择先手；
- `PLAYER_ACTION`：正式出牌阶段；
- `BOSS_ACTION`：boss 行动中；
- `ROUND_SETTLEMENT`：回合结算阶段；
- `RECONNECT_WAIT`：等待重连；
- `REVIVE_WAIT`：一名玩家死亡、另一名玩家存活，等待复活；
- `FINISHED`：对局已结束；

前端和测试都应以此为准，不要只按旧注释中的四个状态理解。

- `firstPlayerUserId`：本回合先手玩家 userId；

### 13.5 第一阶段联调检查

1. 两名用户接受邀请并进入同一房间。

3. 第一名玩家准备后，房间暂时不应创建对局。

### 13.6 复活后的状态与手牌测试

当一名玩家死亡且另一名玩家存活时，后端不会立即结束对局，而是将对局置为 `REVIVE_WAIT`，默认等待复活 30 秒。

测试步骤：

1. 让霸凌者攻击使一名玩家的 `currentHp` 降为 `0`；
2. 确认 `GET /api/matches/{matchId}` 返回 `phase=REVIVE_WAIT`；
3. 确认存活队友仍为 `ACTIVE`，对局 `status=1`；
4. 调用 `GET /api/matches/{matchId}/revive/status?userId={deadUserId}`；
5. 确认 `canRevive=true`；
6. 调用复活请求接口；
7. 确认响应 `afterHp` 在 `10~20` 范围内，且不超过该玩家 `maxHp`；
8. 再次调用对局状态接口，确认 `phase=PLAYER_ACTION`；
9. 确认双方 `endedTurn=0`，存活玩家行动点恢复为基础行动点；
10. 确认双方手牌不足 5 张时分别补牌，当前登录用户的 `hand` 已更新；
11. 确认双方都死亡或 30 秒内未复活时，对局进入 `FINISHED`。

### 13.7 选择先手接口

当前版本已新增先手选择步骤：双方在进入对局页并看到各自手牌后，再由房主发起先手选择。后端在收到选择请求后，会更新当前对局的先手阶段状态，并向双方推送先手结果，随后进入正式出牌阶段。

- **Method**: `POST`
- **URL**: `/api/matches/{matchId}/choose-first-player`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Content-Type**: `application/json`

#### 请求体

```json
{
  "firstPlayerUserId": 3
}
```

#### 响应示例

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "matchId": 12,
    "roundNo": 1,
    "chosenByUserId": 3,
    "firstPlayerUserId": 3,
    "secondPlayerUserId": 9,
    "version": 1,
    "phase": "PLAYER_ACTION"
  }
}
```

#### 接口规则

- 当前仅允许处于 `SELECT_FIRST_PLAYER` 阶段时调用；
- 当前实现默认由房主发起选择；
- `firstPlayerUserId` 必须是本对局房间中的成员；
- 选择完成后，对局阶段会切换为 `PLAYER_ACTION`；
- 双方 WebSocket 应收到 `match.first_player.chosen` 事件。

#### 测试步骤

1. 两名玩家完成组队并进入对局页。
2. 确认双方都已收到各自手牌。
3. 由房主调用 `POST /api/matches/{matchId}/choose-first-player`。
4. 请求体中传入希望先出牌的玩家 `userId`。
5. 检查返回值中是否包含正确的 `firstPlayerUserId`、`secondPlayerUserId`、`phase`。
6. 检查双方 WebSocket 是否收到 `match.first_player.chosen`。
7. 调用 `GET /api/matches/{matchId}`，确认 `phase` 已切换为 `PLAYER_ACTION`。
8. 如果后续发生断线，重新调用 `GET /api/matches/{matchId}`，检查是否返回：
   - `waitingReconnect = true`
   - `reconnectRemainingSeconds > 0`
9. 非房主再次调用该接口，确认返回无权操作或当前阶段不允许选择。
10. 传入非房间成员的 `userId`，确认请求被拒绝。

### 13.7 退出并关闭未开始房间

- **Method**: `POST`
- **URL**: `/api/rooms/{roomId}/leave`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Body**: 无

任意房间成员可在正式对局开始前调用。由于当前是双人组队房间，一方退出会关闭整个房间，并同步处理双方成员关系：

```text
game_rooms.status = 3
game_rooms.closed_at = 当前时间
game_rooms.player_count = 0
room_members.left_at = 当前时间
room_members.ready_status = 0
room_members.online_status = 0
```

双方收到：

```json
{
  "type": "room.closed",
  "data": {
    "roomId": 12,
    "closedByUserId": 3,
    "closedAt": "2026-07-25T12:00:00"
  }
}
```

并向双方好友广播新的 `friend.presence.changed`。WebSocket 仍连接时，退出后的状态应为 `IDLE`、`invitable=true`。

接口规则：

- 非房间成员调用返回无权操作；
- 房间已经关闭时幂等返回当前房间详情；
- 房间已经绑定 `matchId` 或 `status=2` 时拒绝普通退出，应使用后续投降/中断对局流程；
- 页面跳转或返回大厅前，前端应主动调用该接口，不能只修改本地路由。

### 13.8 房间自动清理与断线兜底方案

为解决“用户关闭页面后房间仍显示准备中，导致下次无法重新邀请”的问题，当前项目建议在已存在的 WebSocket 心跳基础上，补齐房间回收链路。核心原则是：**在线状态、房间占用状态、成员状态必须联动**。

#### 13.7.1 现有基础

当前后端已经具备：

- WebSocket 连接建立 / 断开回调；
- `ws.heartbeat` 心跳消息；
- 用户在线状态广播；
- 房间详情与成员表；
- 退出房间接口 `/api/rooms/{roomId}/leave`；
- 邀请时对“是否在房间 / 是否在对局中”的校验。

这部分缺口现在已经补上了：

- 关闭客户端页面后，WebSocket 断开会立即触发房间成员清理；
- 若断开回调未及时触发，心跳超时任务会继续兜底清理；
- 房间在无人有效成员时会自动关闭，`game_rooms.status` 会从准备中转为已关闭；
- 下次邀请时，后端会先清理失活成员，再判断玩家是否仍在有效房间中。

#### 13.7.2 推荐增加的状态字段

建议至少补充或明确以下字段含义：

- `game_rooms.last_activity_at`：房间最后活跃时间；
- `room_members.last_heartbeat_at`：成员最后一次心跳时间；
- `room_members.left_at`：离开时间，`NULL` 表示仍有效；
- `room_members.online_status`：成员在线状态；
- `game_rooms.status`：`0/1` 表示准备中，`2` 表示对局中，`3` 表示已关闭。

如果不想新增字段，也可以先复用 `updated_at` 作为回收依据，但长期看不如显式字段清晰。

#### 13.7.3 服务端统一收口方法【已实现】

后端已增加统一的回收入口：

```text
handleUserDisconnected(userId, reason)
```

其内部统一处理：

1. 解绑 WebSocket 会话；
2. 更新用户在线状态为离线；
3. 查询该用户当前是否存在有效房间成员记录；
4. 若在准备中房间内，则执行离房；
5. 若房间因此变成空房，则自动关闭房间；
6. 向其他成员广播 `room.closed`；
7. 向好友广播新的 `friend.presence.changed`。

这样 `afterConnectionClosed`、`handleTransportError`、定时任务都可以复用同一套清理逻辑。

#### 13.7.4 WebSocket 断开时的行为【已实现】

当客户端关闭页面、刷新页面、浏览器崩溃或网络断开时，WebSocket 连接会先断开。后端在 `afterConnectionClosed` 中会：

- 调用统一清理方法；
- 如果该用户仍在准备中房间，立即把他从房间移除；
- 如果房间只剩 0 人，直接关闭房间；
- 如果房间还剩 1 人，自动把房间置为已关闭；
- 及时广播房间状态变化，避免前端继续显示“组队中”。

#### 13.7.5 心跳超时兜底【已实现】

心跳不仅用于在线状态，也用于房间回收。当前实现建议保持：

- 前端每 20 秒发送一次 `ws.heartbeat`；
- 后端记录每个用户的最后心跳时间；
- 若超过 60 秒没有心跳，则视为失活；
- 定时任务每 30 秒扫描一次，清理失活用户的房间占用；
- 若房间空了，自动关闭。

这样即使 `afterConnectionClosed` 没有及时触发，最终也会被超时任务兜底清理。

#### 13.7.6 前端联动要求【已完成基础接入】

前端建议同时做两件事：

- 进入房间时建立 WebSocket，并保持心跳；
- 页面卸载前主动调用 `/api/rooms/{roomId}/leave`，作为最快的释放手段。

但前端的主动退出只能作为辅助，最终权威回收仍然以服务端的断开事件和超时任务为准。

#### 13.7.7 测试重点【建议保留】

建议重点测试以下场景：

1. 正常点击退出房间后，成员记录被清理，房间关闭；
2. 直接关闭标签页后，房间在超时内自动释放；
3. 断网后等待心跳超时，房间自动释放；
4. 房间被释放后，再次邀请同一用户应恢复可邀请状态；
5. 房间已进入正式对局时，退出逻辑不能误关房间，应走对局中断 / 投降流程。

### 13.8 基础出牌接口

- **Method**: `POST`
- **URL**: `/api/matches/{matchId}/actions/play-card`
- **Headers**:
  - `Authorization: Bearer {accessToken}`
  - `Content-Type: application/json`

#### 请求示例：攻击霸凌者

```json
{
  "cardInstanceId": 1,
  "targetType": "BOSS",
  "targetUserId": null,
  "clientActionId": "user9-round1-action1",
  "expectedVersion": 1
}
```

#### 请求字段说明

- `cardInstanceId`：本局卡牌实例 ID，来自对局状态的 `hand[].instanceId`；不是卡牌模板 `cardId`。
- `targetType`：目标类型。攻击牌传 `BOSS`，回血和加防牌传 `PLAYER`。当前服务端会根据实际卡牌效果再次校验。
- `targetUserId`：目标玩家 ID。攻击牌必须传 `null`；回血和加防牌必须传本局任一存活玩家的 `userId`。
- `clientActionId`：客户端生成的本次操作唯一编号；同一玩家在同一局内不得重复，用于识别重复提交。
- `expectedVersion`：客户端操作前看到的 `matches.version`。与服务器版本不一致时拒绝操作，前端应重新查询对局。

#### 响应示例

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "matchId": 1,
    "actionId": 1,
    "clientActionId": "user9-round1-action1",
    "actionType": "PLAY_CARD",
    "actorUserId": 9,
    "cardInstanceId": 1,
    "cardId": 59,
    "cardName": "破冰礼遇",
    "effectType": "DAMAGE",
    "effectValue": 2,
    "targetType": "BOSS",
    "targetUserId": null,
    "beforeValue": 50,
    "afterValue": 48,
    "remainingActionPoints": 3,
    "effects": [
      {
        "effectType": "DAMAGE",
        "triggerTiming": "IMMEDIATE",
        "targetType": "BOSS",
        "targetUserId": null,
        "configuredValue": 2,
        "actualValue": 2,
        "beforeValue": 50,
        "afterValue": 48,
        "pending": false,
        "triggerRound": 1,
        "remainingTriggers": 0
      }
    ],
    "version": 2,
    "matchEnded": false,
    "winnerType": 0
  },
  "success": true
}
```

#### 响应字段说明

- `matchId`：发生操作的正式对局 ID。
- `actionId`：写入 `match_actions` 的操作流水 ID。
- `clientActionId`：原样返回客户端操作唯一编号。
- `actionType`：操作类型，当前固定为 `PLAY_CARD`。
- `actorUserId`：实际出牌玩家 ID，由 Token 确定。
- `cardInstanceId`：被打出的本局卡牌实例 ID。
- `cardId`：卡牌模板 ID。
- `cardName`：卡牌名称。
- `effectType`：实际执行的基础效果：`DAMAGE`、`HEAL` 或 `SHIELD`。
- `effectValue`：卡牌配置的效果数值；有效治疗受最大血量限制时可能小于此值。
- `targetType`：实际目标类型：`BOSS` 或 `PLAYER`。
- `targetUserId`：玩家目标 ID；攻击霸凌者时为 `null`。
- `beforeValue`：目标属性变化前数值。伤害对应霸凌者血量，回血对应玩家血量，加防对应玩家防御。
- `afterValue`：目标属性变化后数值。
- `remainingActionPoints`：出牌者扣费后剩余员工调用机会。
- `effects`：本次卡牌的完整结构化效果列表，既包含已经执行的立即效果，也包含写入待处理表的延迟效果。
  - `effectType`：`DAMAGE_BOSS`、`HEAL_PLAYER`、`ADD_SHIELD` 或 `ADD_ACTION_POINTS`。
  - `triggerTiming`：`IMMEDIATE` 表示立即执行，`ROUND_START` 表示指定回合开始执行。
  - `targetType`：效果目标类型，`BOSS` 或 `PLAYER`。
  - `targetUserId`：玩家目标 ID；霸凌者目标时为 `null`。
  - `configuredValue`：卡牌模板配置的效果值。
  - `actualValue`：本次真正产生的值；回血受最大血量限制时可能更小，待执行效果当前为 `0`。
  - `beforeValue`：立即效果执行前的目标数值；待执行效果为 `null`。
  - `afterValue`：立即效果执行后的目标数值；待执行效果为 `null`。
  - `pending`：是否已写入 `match_pending_effects` 等待后续回合执行。
  - `triggerRound`：效果执行回合；立即效果为当前回合。
  - `remainingTriggers`：剩余触发次数。
- `version`：操作成功后的新对局状态版本，下一次操作应传此值。
- `matchEnded`：本次操作是否直接结束对局。
- `winnerType`：`0` 未结束、`1` 玩家胜利、`2` 玩家失败、`3` 异常中断。

#### 卡牌效果映射说明

当前数据库仍保留旧字段，基础出牌闭环暂按以下规则解释：

- `satisfaction_change > 0`：对霸凌者造成等量伤害；
- `confidence_change > 0`：给指定玩家恢复等量血量，不超过 `maxHp`；
- `shield_change > 0`：给指定玩家增加防御；
- `card_type=defend` 且 `rage_change < 0`：第一版兼容映射为增加 `abs(rage_change)` 点防御。

复杂持续效果文字暂时不执行，只执行卡牌基础字段中的立即数值。

#### 攻击牌测试

1. 调用 `GET /api/matches/{matchId}`，从自己的 `hand` 选择 `satisfactionChange` 对应伤害牌，并记录 `version`。
2. 使用该牌的 `instanceId` 调用出牌接口，目标传 `BOSS`、`targetUserId=null`。
3. 检查霸凌者血量降低、卡牌进入 `DISCARD`、员工调用机会按 `cost` 扣除。
4. 再次查询对局，检查响应 `version` 已递增，自己的 `handCount` 减少 1，`discardCount` 增加 1。

#### 回血牌测试

1. 先准备一名未满血的本局玩家数据。
2. 选择使用 `confidence_change > 0` 的手牌。
3. 请求传 `targetType=PLAYER` 和目标 `targetUserId`。
4. 检查目标血量增加且不超过 `maxHp`。

#### 加防牌测试

1. 选择 `shield_change > 0`，或 `card_type=defend` 且 `rage_change<0` 的手牌。
2. 指定本局存活玩家作为目标。
3. 检查目标 `shield` 增加，卡牌进入弃牌堆，费用被扣除。

#### WebSocket 通知

双方会收到：

```json
{
  "type": "card.played",
  "data": {
    "matchId": 1,
    "actorUserId": 9,
    "cardInstanceId": 1,
    "effectType": "DAMAGE",
    "version": 2
  }
}
```

通知中的 `data` 字段与 HTTP 出牌响应的 `data` 相同。前端发现版本不连续时，应重新调用 `GET /api/matches/{matchId}`。

#### 胜利闭环测试

1. 在测试数据库中将当前对局 `boss_current_hp` 调整到某张攻击牌伤害以内。
2. 使用该攻击牌出牌。
3. 预期 `matchEnded=true`、`winnerType=1`。
4. 检查 `matches.status=2`、`matches.phase=FINISHED`、`game_rooms.status=3`。
5. 双方应收到 `match.ended`，好友应收到玩家状态变化广播。

#### 常见失败测试

- 使用队友卡牌实例：提示卡牌不在当前玩家手牌中；
- 重复使用已进入弃牌堆的实例：提示卡牌不在当前玩家手牌中；
- 费用超过剩余员工调用机会：提示员工调用机会不足；
- 部门不匹配：提示当前部门不能使用该卡牌；
- 攻击牌传玩家目标：提示攻击牌目标必须是霸凌者；
- 回血或加防不传目标：提示必须选择玩家目标；
- `expectedVersion` 过期：提示刷新后重试；
- 重复 `clientActionId`：提示该出牌请求已处理。

- `allPlayersEnded`：本次操作后双方是否都已结束。

- `winnerType`：`0` 未结束、`1` 玩家胜、`2` 玩家负、`3` 异常中断。
- `currentRound`：处理完成后的当前回合；成功进入下一回合时加 1。
- `phase`：处理完成后的阶段；继续游戏时回到 `PLAYER_ACTION`，结束时为 `FINISHED`。
- `version`：处理后的新状态版本。
- `handCount`：当前操作玩家处理后的手牌数；下一回合正常抽满为 5。
- `deckCount`：当前操作玩家处理后的牌堆数。
- `discardCount`：当前操作玩家处理后的弃牌堆数。

#### `bossAttackTargets` 字段说明

- `userId`：被攻击玩家 ID。
- `attack`：霸凌者本回合最终攻击力。
- `shieldBefore`：受击前防御值。
- `absorbedDamage`：本次被防御吸收的伤害。
- `hpBefore`：受击前血量。
- `hpDamage`：实际扣除的血量。
- `hpAfter`：受击后血量，最低为 0。
- `dead`：该玩家是否因本次攻击死亡。

#### 完整一回合测试

1. 双方查询 `GET /api/matches/{matchId}` 并记录最新 `version`。
2. 玩家 A 出若干牌，然后调用结束回合；检查剩余手牌全部进入弃牌堆，且不能继续出牌。
3. 玩家 B 使用响应中的最新 `version` 查询权威状态，再调用结束回合。
4. 检查霸凌者同时攻击两名玩家，伤害先由 `shield` 吸收，剩余部分扣血。
5. 检查攻击完成后双方 `shield=0`。
6. 如果双方存活，检查 `currentRound+1`、`actionPoints` 重置、`endedTurn=0`，并各抽 5 张。
7. 检查旧回合 `round_status=1`，新回合存在且 `round_status=0`。

#### 顾客效果测试

每次新回合开始时按本局顾客 `triggerChance` 独立判定：

- `bully_attack_down`：触发后降低本回合霸凌者攻击，最低为 0；
- `bully_attack_up`：触发后提高本回合霸凌者攻击；
- `bully_hp_up`：触发后增加霸凌者最大血量和当前血量。
- `player_hp_up`：触发后给两名仍存活的护卫各恢复血值，不超过各自上限，不会复活已倒下的玩家。

查询对局时检查：

- `customerTriggered`：`1` 表示新回合判定触发；
- `customerEffectType`：触发机制类型；
- `customerEffectValue`：配置数值；
- `bossCurrentAttack`：本回合顾客修正后的最终攻击。

#### 弃牌重洗测试

1. 连续结束多个回合，直到牌堆不足 5 张。
2. 下一回合抽牌时，后端会将弃牌堆随机洗回牌堆后继续抽取。
3. 预期在全部 20 张牌均可循环使用的情况下，每个新回合尽量保持 5 张手牌。

#### 失败闭环测试

1. 在测试环境将任一玩家 `current_hp` 调整到不高于霸凌者攻击力。
2. 双方结束回合。
3. 预期对应玩家 `dead=true`、`playerStatus=DEAD`。
4. 预期 `matchEnded=true`、`winnerType=2`、`phase=FINISHED`。
5. 检查 `matches.status=2`、`game_rooms.status=3`，双方个人 `result_type=2`。

#### WebSocket 事件

- `player.turn.ended`：任一玩家结束回合后发送；
- `boss.attack.resolved`：双方结束且霸凌者伤害完成后发送；
- `round.started`：双方存活并创建下一回合后发送；
- `match.ended`：任一玩家死亡、对局失败时发送。

上述事件的 `data` 与结束回合 HTTP 响应相同。前端仍应根据 `version` 判断是否需要重新查询权威状态。

#### 结构化卡牌效果测试

当前出牌已经以 `card_effects` 为唯一效果配置来源，不再读取 `cards` 中旧的满意度、信心值、怒气值或防御变化字段。

出牌响应中的 `effects` 是效果结果数组，每项字段含义如下：

- `effectType`：效果类型，支持 `DAMAGE_BOSS`、`HEAL_PLAYER`、`ADD_SHIELD`、`ADD_ACTION_POINTS`、`MULTIPLY_NEXT_CARD`；
- `triggerTiming`：触发时机，`IMMEDIATE` 表示立即执行，`ROUND_START` 表示指定回合开始时执行，`NEXT_CARD` 表示等待来源玩家打出下一张牌；
- `targetType`：实际作用目标类型，`BOSS` 或 `PLAYER`；
- `targetUserId`：玩家目标 ID，目标为霸凌者时为 `null`；
- `baseValue`：模板中配置的原始效果数值；
- `actualValue`：考虑翻倍和血量上限后实际执行或排期的数值；
- `beforeValue`：立即效果执行前的属性值；排期效果尚未执行时为 `null`；
- `afterValue`：立即效果执行后的属性值；排期效果尚未执行时为 `null`；
- `scheduled`：是否已经写入 `match_pending_effects` 等待以后执行；
- `triggerRound`：立即效果为当前回合，延迟效果为计划执行回合；
- `pendingEffectId`：待处理效果记录 ID，立即效果为 `null`。

出牌响应新增或调整：

- `appliedMultiplier`：本次卡牌效果倍率，普通情况为 `1`，消耗 `L-02` 后为 `2`；
- `effects`：本次卡牌的全部立即和排期效果；
- 原单一的 `effectType/effectValue/beforeValue/afterValue` 已由 `effects` 数组替代。

##### 下回合效果测试

1. 使用 `S-03`、`S-05`、`O-02`、`O-05`、`O-10`、`O-11`、`O-12`、`O-14` 或 `O-15`；
2. 检查响应中同时存在 `scheduled=false` 的立即效果和 `scheduled=true` 的 `ROUND_START` 效果；
3. 检查 `match_pending_effects.status=PENDING` 且 `trigger_round=当前回合+1`；
4. 双方结束回合进入下一回合；
5. 检查延迟伤害、回血或防御已经执行；
6. 检查该记录变为 `RESOLVED`。

##### 员工调用机会测试

1. 使用 `O-06`，检查打出当回合员工调用机会先增加 1，再扣除卡牌费用；
2. 下一回合重置基础行动点后，再执行排期的 `ADD_ACTION_POINTS +1`；
3. 使用 `L-01` 时，本回合增加 2，下一回合增加 1。

##### 下一张牌翻倍测试

1. 打出 `L-02`，检查生成 `MULTIPLY_NEXT_CARD/NEXT_CARD` 的 `PENDING` 记录；
2. 同一玩家打出下一张数值效果牌；
3. 第二张牌响应 `appliedMultiplier=2`；
4. 立即效果和该牌创建的下回合效果数值都应翻倍；
5. `L-02` 对应待处理记录应变为 `RESOLVED`；
6. 再打第三张牌时 `appliedMultiplier` 应恢复为 `1`。

##### 延迟伤害胜利测试

如果下回合开始时 `DAMAGE_BOSS` 将霸凌者血量降到 0：

- 对局应立即结束；
- `matches.status=2`；
- `matches.phase=FINISHED`；
- `winnerType=1`；
- 不再为双方抽取新回合手牌。

## 14. 好友在线状态与掉线重连说明

### 14.1 当前实现方式

当前项目的好友在线状态不再依赖数据库中的临时标志，而是由下面三部分共同决定：

- WebSocket 连接是否存在；
- Redis 中是否还有该用户的有效 Presence 记录；
- 用户是否处于有效房间或真实进行中的对局中。

因此好友列表返回的：

```json
{
  "onlineStatus": 1,
  "presenceStatus": "IDLE",
  "invitable": true
}
```

并不是写死在数据库里的，而是后端每次动态计算出来的。

### 14.2 真实状态判断规则

当前规则与实现一致：

1. WebSocket Presence 不存在时，返回 `OFFLINE`；
2. 存在未离开的房间成员记录，并且房间绑定的正式对局真实存在且 `matches.status=1`、`ended_at IS NULL`、`phase != FINISHED`，返回 `IN_MATCH`；
3. 存在未离开的房间成员记录，并且房间 `status=0/1`，返回 `IN_ROOM`；
4. 其他在线用户返回 `IDLE`。

注意：`match_id` 非空不再单独代表“正在游戏中”，必须结合 `matches` 的真实状态判断。

### 14.3 当前 Redis Presence 作用

Redis Presence 主要用于：

- 判断用户是否在线；
- 支持多个浏览器窗口同时在线；
- 支持 60 秒超时离线；
- 支持 WebSocket 断开后的自动清理。

当前代码里不会使用下面这种旧式房间在线 Key 来判断好友状态：

```text
room:online:{roomCode}:{userId}
match:online:{matchCode}:{userId}
```

这些更像早期设计草案，现阶段应以 `friend.presence.changed`、`GET /api/friends`、`GET /api/rooms/{roomId}` 和 `GET /api/matches/{matchId}` 为准。

### 14.4 掉线和重连

- 关闭标签页、刷新页面、浏览器崩溃后，WebSocket 会先断开；
- Redis Presence 会在 60 秒内过期；
- 如果用户重新连接并且仍有有效房间或有效对局，Presence 会重新计算；
- 如果没有有效房间和有效对局，则恢复为 `IDLE` 或 `OFFLINE`。

### 14.5 测试建议

#### 测试 1：登录后在线

1. 用户登录并建立 WebSocket；
2. 调用 `GET /api/friends`；
3. 好友应显示 `onlineStatus=1`。

#### 测试 2：进入房间后显示组队中

1. 两名好友接受邀请进入同一房间；
2. 调用 `GET /api/friends`；
3. 好友应显示 `presenceStatus=IN_ROOM`。

#### 测试 3：进入正式对局后显示游戏中

1. 两名玩家都选择部门并准备；
2. 等待 `match.started`；
3. 调用 `GET /api/friends`；
4. 好友应显示 `presenceStatus=IN_MATCH`。

#### 测试 4：退出未开始房间后恢复为空闲

1. 在正式对局开始前调用 `POST /api/rooms/{roomId}/leave`；
2. 再次调用 `GET /api/friends`；
3. 好友应恢复 `presenceStatus=IDLE`。

## 16. 组队到结算完整流程测试总览

本章给出一个从“组队”到“出牌、结束回合、打败霸凌者、结算”的完整测试流程。建议使用两个浏览器窗口，分别登录两个互为好友的账号，例如用户 11 和用户 14，并都保持 WebSocket 连接。

### 15.1 测试前准备

1. 启动 MySQL、Redis、RabbitMQ、后端服务；
2. 确认两个账号互为好友；
3. 准备两个浏览器窗口或一个普通窗口加一个无痕窗口；
4. 两个窗口都输入各自的 `accessToken` 并建立 WebSocket；
5. 确认两个窗口都收到：

```json
{
  "type": "ws.connected"
}
```

### 15.2 邀请与接受邀请

#### 发送邀请

- **Method**: `POST`
- **URL**: `/api/rooms/invites`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Content-Type**: `application/json`

#### 请求体字段

```json
{
  "friendId": 14
}
```

字段说明：

- `friendId`：被邀请人的用户 ID，必须是好友且在线空闲；

#### 发送邀请成功后需要检查

1. 返回的 `room_invites.id` 是否存在；
2. 被邀请人的 WebSocket 是否收到 `room.invite.created`；
3. 数据库 `room_invites.status=0`；
4. 如果对方不在 `IDLE`，接口应报错，不应创建邀请。

#### 接受邀请

- **Method**: `POST`
- **URL**: `/api/rooms/invites/{inviteId}/accept`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 请求体

无。

#### 接受邀请后需要检查

1. 返回的 `roomId` 是否存在；
2. `game_rooms.status=1`；
3. `game_rooms.player_count=2`；
4. 双方 `room_members.left_at IS NULL`；
5. 双方 WebSocket 是否收到 `room.created` 或相应 Presence 变化；
6. 好友列表中双方应显示 `IN_ROOM`；
7. 如果浏览器页面跳转失败，数据库房间仍然成立，前端要重新查询房间详情恢复。

### 15.3 退出未开始房间

#### 退出接口

- **Method**: `POST`
- **URL**: `/api/rooms/{roomId}/leave`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 请求体

无。

#### 退出后检查

1. `game_rooms.status=3`；
2. `game_rooms.closed_at` 非空；
3. `room_members.left_at` 非空；
4. 双方好友状态恢复为 `IDLE` 或离线；
5. 两端收到 `room.closed`；
6. 前端应清空当前 `roomId` 并返回大厅。

#### 注意

- 已经开始正式对局后，普通退出接口会拒绝；
- 页面刷新或客户端关闭不会自动调用该接口；
- 若想让房间自动回收，还需要额外的超时清理逻辑。

### 15.4 选择部门

#### 接口

- **Method**: `POST`
- **URL**: `/api/rooms/{roomId}/department`
- **Headers**: `Authorization: Bearer {accessToken}`
- **Content-Type**: `application/json`

#### 请求体

```json
{
  "deptType": "sales"
}
```

#### 字段说明

- `deptType`：部门类型，只能是 `sales` 或 `purchase`；
- 两名玩家必须选择不同部门；
- 部门校验失败时接口会报错。

#### 选择后检查

1. `room_members.dept_type` 是否更新；
2. 房间详情接口里部门是否正确展示；
3. WebSocket 是否收到 `room.member.department.changed`。

### 15.5 准备并创建正式对局

#### 接口

- **Method**: `POST`
- **URL**: `/api/rooms/{roomId}/ready`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 请求体

无。

#### 准备成功后检查

1. 第一名玩家准备后，房间不应立即进入正式对局；
2. 第二名玩家准备后，响应中应返回非空 `matchId`；
3. `game_rooms.status` 应变为 `2`；
4. 双方收到 `match.started`；
5. 前端应读取 `matchId` 并立即调用 `GET /api/matches/{matchId}`；
6. 如果 WebSocket 丢消息，以 HTTP 查询结果为准。

### 15.6 查询正式对局状态

#### 接口

- **Method**: `GET`
- **URL**: `/api/matches/{matchId}`
- **Headers**: `Authorization: Bearer {accessToken}`

#### 响应体重点字段

- `matchId`：正式对局 ID；
- `status`：对局是否进行中；
- `phase`：当前阶段，`PLAYER_ACTION` 时可以出牌；
- `currentRound`：当前回合；
- `version`：当前操作版本；
- `customer`：当前顾客信息；
- `bossCurrentHp`、`bossCurrentAttack`：霸凌者血量和攻击；
- `players`：双方玩家状态；
- `hand`：当前操作者手牌。

#### 前端处理建议

1. 进入对局后先拉一次权威状态；
2. 将 `matchId`、`version`、`hand` 保存到页面状态；
3. 后续出牌和结束回合都使用最新 `version`；
4. 每次收到 `match.started`、`card.played`、`player.turn.ended`、`boss.attack.resolved`、`round.started`、`match.ended` 也可以重新查询一次。

### 15.7 出牌

#### 接口

- **Method**: `POST`
- **URL**: `/api/matches/{matchId}/actions/play-card`
- **Headers**:
  - `Authorization: Bearer {accessToken}`
  - `Content-Type: application/json`

#### 请求体字段

```json
{
  "cardInstanceId": 101,
  "targetType": "PLAYER",
  "targetUserId": 11,
  "clientActionId": "match3-user14-play-101-001",
  "expectedVersion": 1
}
```

字段说明：

- `cardInstanceId`：本局卡牌实例 ID，来自 `GET /api/matches/{matchId}` 的 `hand[].instanceId`；不是模板 `cardId`；
- `targetType`：目标类型，攻击霸凌者传 `BOSS`，回血和加防传 `PLAYER`；
- `targetUserId`：玩家目标 ID；攻击牌传 `null`，玩家效果传本局存活玩家 ID；
- `clientActionId`：客户端自己生成的唯一操作编号；
- `expectedVersion`：客户端认为当前对局应有的版本；必须与服务器一致。

#### 出牌成功后需要关注的字段

- `remainingActionPoints`：出牌后剩余行动点；
- `appliedMultiplier`：本次卡牌是否被倍率效果影响；
- `effects`：本次卡牌实际产生的效果数组；
- `version`：出牌后新的对局版本；
- `matchEnded`：本次出牌是否直接结束对局；
- `winnerType`：结算结果类型。

#### 响应处理建议

1. 先检查 `success=true`；
2. 读取新的 `version`；
3. 刷新 `hand`、`players`、`bossCurrentHp` 等展示；
4. 如果 `matchEnded=true`，不要再继续出牌，直接进入结算界面；
5. 如果响应里出现多个 `effects`，说明这张牌触发了多个结构化效果，需要逐项展示。

### 15.8 结束回合

#### 接口

- **Method**: `POST`
- **URL**: `/api/matches/{matchId}/actions/end-turn`
- **Headers**:
  - `Authorization: Bearer {accessToken}`
  - `Content-Type: application/json`

#### 请求体

```json
{
  "clientActionId": "match3-user14-end-001",
  "expectedVersion": 2
}
```

字段说明：

- `clientActionId`：结束回合唯一编号；
- `expectedVersion`：调用结束回合前看到的最新版本。

#### 结束回合后需要检查

1. 当前玩家剩余手牌是否进入弃牌堆；
2. `endedTurn` 是否从 `0` 变成 `1`；
3. 如果双方都结束，霸凌者是否同时攻击两人；
4. 如果双方都存活，是否创建下一回合；
5. `version` 是否递增；
6. `round.started`、`boss.attack.resolved`、`match.ended` 等 WebSocket 是否正常发送。

### 15.9 打败霸凌者与结算

#### 胜利条件

当霸凌者血量降为 0 时，响应中通常会出现：

- `matchEnded=true`
- `winnerType=1`

#### 胜利后检查

1. `matches.status=2`；
2. `matches.phase=FINISHED`；
3. `matches.ended_at` 非空；
4. `game_rooms.status=3`；
5. `game_rooms.closed_at` 非空；
6. 双方 `room_members.left_at` 非空；
7. 好友状态恢复为 `IDLE` 或离线；
8. 双方收到 `match.ended`；
9. 前端进入结算页或结算提示。

#### 失败条件

如果任一玩家在霸凌者攻击阶段死亡：

- `winnerType=2`；
- `matchEnded=true`；
- 房间和成员关系也会被同步关闭。

### 15.10 WebSocket 与 HTTP 的配合原则

在整个流程中，建议遵循下面顺序：

1. 先用 WebSocket 监听实时变化；
2. WebSocket 收到关键事件后，再用 HTTP 拉权威状态；
3. 出牌、结束回合、退出房间这类操作以后，都以 HTTP 响应为主；
4. 如果 WebSocket 消息和 HTTP 状态不一致，以 HTTP 为准；
5. 如果版本不连续，立即重新调用 `GET /api/matches/{matchId}`。
