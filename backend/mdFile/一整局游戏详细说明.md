# 一整局游戏详细说明

本文档基于当前后端实现，详细梳理从双方准备开始，到正式对局、断线重连、结算结束的完整流程。本文只描述当前代码已经实现的功能，不额外假设未实现能力。

---

## 1. 参与的核心对象

### 1.1 房间相关

- `game_rooms`：房间主表。
- `room_members`：房间成员表。
- `room_invites`：邀请表。

### 1.2 对局相关

- `matches`：对局主表。
- `match_players`：对局玩家表。
- `match_rounds`：对局回合表。
- `match_cards`：对局卡牌实例表。
- `match_actions`：对局动作日志表。
- `match_pending_effects`：延迟效果表。

### 1.3 基础配置相关

- `customer_types`：顾客模板。
- `bullies`：霸凌者模板。
- `cards`：卡牌模板。
- `card_effects`：卡牌效果定义。
- `deck_card_configs`：部门牌组配置。

---

## 2. 总体流程概览

一个完整局的生命周期大致如下：

1. 两名玩家进入同一房间；
2. 双方分别选择部门；
3. 双方分别点击准备；
4. 后端校验人数、准备状态、部门合法性；
5. 后端创建 `matches`、`match_players`、`match_cards`、`match_rounds`；
6. 房间状态切换为对战中；
7. 双方 WebSocket 收到 `match.started`；
8. 双方进入对局页，查看自己的手牌；
9. 房主在“选择先手”阶段提交先手选择；
10. 进入正式出牌阶段；
11. 玩家依次出牌、结束回合；
12. 当双方都结束回合后，boss 进行攻击；
13. 若 boss 或玩家死亡，则对局结束；
14. 读取结算接口，进入结算页；
15. 房间状态与玩家在线状态最终收尾。

## 5. 双方准备并触发开局

### 5.1 接口

- `POST /api/rooms/{roomId}/ready`

### 5.2 当前代码的开局条件

后端在 `initializeMatch(roomId)` 中会校验：

1. 房间必须正好两个人；
2. 双方 `ready_status = 1`；
3. 一方必须是 `sales`，另一方必须是 `purchase`；
4. 必须有可用顾客模板；
5. 必须有可用霸凌者模板；
6. 每个部门必须能凑齐 20 张牌。

### 5.3 开局时写入的核心表

#### `matches`

创建一条新对局记录，写入：

- `room_id`
- `customer_type_id`
- `bully_id`
- `boss_name`
- `boss_max_hp`
- `boss_current_hp`
- `boss_base_attack`
- `boss_current_attack`
- `phase = SELECT_FIRST_PLAYER`
- `status = 1`
- `current_round = 1`
- `version`
- `started_at`

#### `match_players`

为两名玩家各写一条：

- `match_id`
- `user_id`
- `seat_no`
- `dept_type`
- `max_hp`
- `current_hp`
- `shield = 0`
- `base_action_points = 3`
- `action_points = 3`
- `ended_turn = 0`
- `player_status = ACTIVE`
- `initial_confidence`
- `final_confidence`
- `initial_funds = 3`
- `total_funds_used = 0`
- `cards_played_count = 0`
- `damage_dealt = 0`
- `damage_taken = 0`
- `healing_done = 0`
- `shield_granted = 0`
- `result_type = 0`

#### `match_cards`

每名玩家生成 20 张牌：

- 5 张进初始手牌，`zone = HAND`
- 15 张进牌库，`zone = DECK`
- `drawn_round` 对初始手牌为 1
- `deck_order` 用于牌库顺序

#### `match_rounds`

创建第 1 回合：

- `round_no = 1`
- `round_status = 0`
- `phase = SELECT_FIRST_PLAYER`
- `boss_attack = bossCurrentAttack`
- `customer_triggered = 0`
- `customer_effect_type = customer.effectType`
- `customer_effect_value = customer.effectValue`
- `boss_rage_value = 0`
- `satisfaction_delta = 0`
- `funds_per_player = 3`
- `started_at`

#### `game_rooms`

房间绑定对局，并切换状态：

- `match_id = 新 matchId`
- `status = 2`

## 9. 选择先手

### 9.1 接口

- `POST /api/matches/{matchId}/choose-first-player`

### 9.2 请求体

```json
{
  "firstPlayerUserId": 3
}
```

### 9.3 当前代码规则

当前实现是一个**后端权威的状态切换接口**，不是单纯给前端做本地展示用的逻辑。它的职责是：

1. 只能在 `phase = SELECT_FIRST_PLAYER` 时调用；
2. 当前只有房主可以选择先手；
3. `firstPlayerUserId` 必须是房间成员；
4. 选择成功后，后端会把对局正式切换到 `PLAYER_ACTION`；
5. 后端会写库、广播结果，并且让双方后续都以同一份状态为准。

### 9.4 数据库写入

#### `matches`

- `phase` 从 `SELECT_FIRST_PLAYER` 改成 `PLAYER_ACTION`
- `version + 1`

#### `match_rounds`

- `first_player_user_id = 先手玩家 userId`
- `chosen_by_user_id = 房主 userId`
- 当前回合 `phase` 改成 `PLAYER_ACTION`
- `customer_triggered = 0`
- `customer_effect_type = NULL`
- `customer_effect_value = 0`
- `started_at = now`

### 9.5 前端职责

前端不应该自己“记住谁是先手”，而应该：

1. 调用该接口提交先手选择；
2. 使用接口返回值渲染界面；
3. 监听 `match.first_player.chosen`；
4. 必要时重新调用 `GET /api/matches/{matchId}` 作为权威状态恢复；
5. 在页面刷新、断线重连后仍能正确恢复先手结果。

### 9.6 WebSocket 通知

双方会收到：

- `match.first_player.chosen`

通知内容应告诉前端：

- 谁被选为先手；
- 谁是发起选择的人；
- 当前对局阶段已经切换为正式出牌阶段。

### 9.7 读取先手信息

前端和后端在 `GET /api/matches/{matchId}` 时，可以从当前回合中读取：

- `firstPlayerUserId`
- `firstPlayerChosenByUserId`

这样刷新页面、重连后也能恢复先手状态。

### 9.5 WebSocket 通知

双方会收到：

- `match.first_player.chosen`

### 9.6 响应体

返回：

- `matchId`
- `roundNo`
- `chosenByUserId`
- `firstPlayerUserId`
- `secondPlayerUserId`
- `version`
- `phase`

## 10. 正式出牌阶段

### 10.1 出牌接口

- `POST /api/matches/{matchId}/actions/play-card`

### 10.2 请求体核心字段

- `cardInstanceId`
- `targetUserId`
- `expectedVersion`
- `clientActionId`

### 10.3 出牌时的校验

后端会校验：

1. 对局必须处于 `PLAYER_ACTION`；
2. `expectedVersion` 必须匹配当前 `match.version`；
3. 当前玩家必须属于这局；
4. 当前玩家必须在线且未死亡；
5. 手中的卡牌必须属于自己；
6. 卡牌必须启用；
7. 当前部门必须允许使用该卡；
8. 行动点必须足够。

### 10.4 出牌时写入数据库

#### `match_actions`

写入一次完整动作日志，包括：

- `action_type = PLAY_CARD`
- `actor_user_id`
- `card_instance_id`
- `card_id`
- `target_user_id`
- `before_value`
- `after_value`
- `delta_value`
- `extra_data`

#### `match_cards`

根据卡牌效果，实例卡会从：

- `HAND`

变为：

- `DISCARD`

#### `match_players`

如果是资源消耗类出牌，还可能更新：

- `action_points`
- `cards_played_count`
- `damage_dealt`
- `healing_done`
- `shield_granted`
- `total_funds_used`

#### `matches`

- `version + 1`

### 10.5 出牌接口响应

`MatchActionResp` 关键字段：

- `matchId`
- `actionId`
- `clientActionId`
- `actionType`
- `actorUserId`
- `cardInstanceId`
- `cardId`
- `cardName`
- `targetType`
- `targetUserId`
- `remainingActionPoints`
- `appliedMultiplier`
- `effects`
- `version`
- `matchEnded`
- `winnerType`

### 10.6 WebSocket 通知

双方收到：

- `card.played`

## 11. 结束回合

### 11.1 接口

- `POST /api/matches/{matchId}/actions/end-turn`

### 11.2 请求体核心字段

- `expectedVersion`
- `clientActionId`

### 11.3 结束回合时发生什么

后端会：

1. 校验对局阶段；
2. 校验版本；
3. 校验幂等请求；
4. 将当前玩家全部手牌弃入弃牌堆；
5. 设置玩家 `ended_turn = 1`；
6. 写入 `match_actions`；
7. 判断双方是否都结束；
8. 如果都结束，则 boss 进行攻击；
9. 若 boss 攻击后有人死亡，则结束对局；
10. 若没结束，则进入下一回合。

### 11.4 数据库写入

#### `match_cards`

当前玩家手牌全部从：

- `HAND`

变为：

- `DISCARD`

#### `match_players`

- `ended_turn = 1`
- 结算时可能更新 `current_hp`
- 结算时可能更新 `player_status`

#### `match_rounds`

如果进入 boss 行动：

- 当前回合 `phase = BOSS_ACTION`

如果回合结束进入下一回合：

- 当前回合状态 `FINISHED`
- 新回合插入一条 `match_rounds`

#### `matches`

- `version + 1`
- 若对局结束，会写 `status = 2`
- `phase = FINISHED`
- `winnerType`
- `endedAt`
- `durationSeconds`

### 11.5 结束回合接口响应

`EndTurnResp` 关键字段：

- `matchId`
- `userId`
- `endedTurn`
- `discardedCount`
- `allPlayersEnded`
- `bossAttackResolved`
- `resolvedRound`
- `bossAttackTargets`
- `matchEnded`
- `winnerType`
- `currentRound`
- `phase`
- `version`
- `handCount`
- `deckCount`
- `discardCount`

### 11.6 WebSocket 通知

可能收到：

- `player.turn.ended`
- `boss.attack.resolved`
- `round.started`
- `match.ended`

## 12. boss 攻击阶段

### 12.1 触发时机

当双方都结束当前回合后，后端触发 boss 攻击。

### 12.2 结算逻辑

当前实现中 boss 结算会：

1. 读取 `bossCurrentAttack`；
2. 对每个玩家计算护盾吸收；
3. 扣除玩家血量；
4. 若血量降到 0，则玩家状态变为 `DEAD`；
5. 写入动作日志 `boss_attack`。

### 12.3 boss 防御

当前已接入 `bullies.defense_value`：

- boss 受到 `DAMAGE_BOSS` 伤害时，会先减去 boss 防御；
- 延迟伤害 `DAMAGE_BOSS` 也会走同样的防御减伤逻辑。

### 12.4 boss 的其他字段

当前 `speedValue`、`rageValue`、`skillData` 仍未接入战斗逻辑，只是数据库预留字段。

---

## 13. 回合推进

如果 boss 攻击后没有人死亡，则进入下一回合：

1. 当前回合标记完成；
2. `match.currentRound + 1`；
3. 重置双方行动点；
4. 清空双方 `endedTurn`；
5. 重新发牌；
6. 创建新的 `match_rounds`；
7. 对局回到 `PLAYER_ACTION`。

---

## 14. 断线与重连

### 14.1 断线触发

当客户端关闭、刷新、断网或崩溃时，WebSocket 断开。

### 14.2 当前实现

断线后，后端会：

1. 清理在线会话；
2. 如果当前用户正处于正式对局，标记其 `match_players.player_status = RECONNECTING`；
3. 对局阶段切换为 `RECONNECT_WAIT`；
4. 对手收到 `match.reconnecting`；
5. `GET /api/matches/{matchId}` 会返回：
   - `waitingReconnect = true`
   - `reconnectRemainingSeconds`

### 14.3 重连接口

- `POST /api/matches/{matchId}/reconnect`

重连成功后：

- 玩家状态恢复为 `ACTIVE`；
- 如果所有人都恢复，则对局阶段回到 `PLAYER_ACTION`；
- 对手收到 `match.recovered`。

### 14.4 超时

当前重连窗口默认：

- `60 秒`

若超过窗口仍未恢复，则按超时失败收尾，对局结束、房间关闭。

---

## 15. 主动放弃

### 15.1 接口

- `POST /api/matches/{matchId}/abandon`

### 15.2 行为

玩家主动放弃后：

1. 玩家状态改为 `LEFT`；
2. 对局立即结束；
3. 执行 `finishMatch`；
4. 对手收到 `match.ended`；
5. 好友状态广播更新。

## 17. 数据库字段写入时机总结

### 17.1 房间阶段

- `room_members.dept_type`：选择部门时写入；
- `room_members.ready_status`：准备时写入；
- `room_members.online_status`：WebSocket 在线/离线时更新；
- `room_members.left_at`：退出或断线清理时写入；
- `game_rooms.status`：根据房间状态变化更新；

### 17.2 对局阶段

- `matches.status / phase / version / currentRound`：在开局、回合推进、结算时更新；
- `match_players.action_points / ended_turn / current_hp / shield / player_status`：出牌、结束回合、boss 攻击、断线重连时更新；
- `match_cards.zone / deck_order / drawn_round`：抽牌、弃牌、洗牌时更新；
- `match_rounds.phase / round_status / started_at / ended_at`：回合切换时更新；
- `match_actions`：每一次出牌、结束回合、boss 攻击都会写日志；
- `match_pending_effects`：延迟效果入队和触发时更新；

- 组队房间；
- 双方准备；
- 对局创建；
- 初始发牌；
