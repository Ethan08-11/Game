# 视频广告复活机制方案

本文档给出一个适合当前项目的“观看视频广告后为血量为 0 的玩家恢复一点血”的实现方案，并整理后端和前端分别需要做哪些修改。

---

## 1. 目标需求

当玩家在对局中血量降到 0 后，不立即结束游戏，而是给玩家一个可选入口：

- 观看一次视频广告；
- 广告观看完成后，允许该玩家恢复 1 点血量；
- 继续留在当前对局中；
- 该功能仅作为“复活/续命”机制，不能无限重复滥用；

---

## 2. 推荐实现思路

### 2.1 核心原则

这个功能本质上是“局内复活”，建议严格由后端判定和落库，前端只负责展示入口与发起请求。

### 2.2 推荐流程

1. 玩家血量降为 0，后端先把玩家标记为“可复活”或“已死亡待结算”；
2. 前端检测到该状态后，弹出“观看广告复活”按钮；
3. 玩家点击按钮后，前端先走广告 SDK/广告页流程；
4. 广告播放完成后，前端拿到一个“已完成观看”的结果；
5. 前端调用后端“申请复活”接口；
6. 后端校验：
   - 该玩家是否在本局中；
   - 当前是否真的处于血量为 0 的状态；
   - 是否还有可用复活次数；
   - 当前对局阶段是否允许复活；
7. 校验通过后，后端把血量加 1，并记录复活次数/时间；
8. 后端广播 WS 消息给双方，前端刷新状态；

---

## 3. 推荐的数据设计

### 3.1 是否需要新增表

如果只是做一个简版“看广告复活一次”，**可以先不新增新表**，直接在现有对局玩家表或对局主表上补字段。

但如果你希望后续支持：

- 每局最多复活几次；
- 每个玩家每天可复活几次；
- 统计广告次数；
- 记录广告回调与审计日志；

那么建议新增一张广告复活日志表。

本方案推荐**新增日志表**，这样后面做广告校验、风控和统计都更方便。

### 3.2 推荐新增字段

#### `match_players` 建议新增

- `revive_count`：本局已复活次数；
- `last_revive_at`：最近一次复活时间；
- `revive_status`：当前是否可复活/已死亡/已复活；

#### `matches` 可选新增

- `dead_player_count`：本局死亡人数统计；
- `revive_enabled`：是否启用广告复活；

#### 可选新增表 `match_revive_logs`

用于记录广告复活的每次动作：

- `id`
- `match_id`
- `round_no`
- `user_id`
- `before_hp`
- `after_hp`
- `status`
- `ad_platform`
- `ad_request_id`
- `ad_callback_raw`
- `created_at`

对应的建表 SQL 已单独生成在 `match_revive_logs.sql`。

## 4. 后端需要做什么

### 4.1 新增复活接口

建议新增两个接口：

#### 1）申请广告复活

```http
POST /api/matches/{matchId}/revive/request
```

请求体示例：

```json
{
  "userId": 15,
  "adRequestId": "ad-20260729-0001"
}
```

作用：
- 前端在广告播放完成后调用；
- 后端检查玩家是否满足复活条件；
- 若满足，则执行恢复血量；
- 同时记录广告请求 ID 和复活日志；

#### 2）查询是否可复活

```http
GET /api/matches/{matchId}/revive/status?userId=15
```

作用：
- 前端在进入对局页或死亡状态时查询；
- 决定是否显示“看广告复活”按钮；
- 返回剩余可复活次数、当前是否可复活等信息；

---

### 4.2 后端需要修改的核心逻辑

#### 1）扣血/死亡判定逻辑

当玩家血量降到 0 时，不要立刻无条件结束整局，而是要：

- 更新该玩家死亡状态；
- 判断当前是否允许广告复活；
- 若允许，则进入“可复活待处理”状态；
- 若不允许或次数已用尽，再结束本局；

#### 2）复活逻辑

在复活接口中：

- 把血量从 0 改成 1；
- 恢复玩家状态为可行动；
- 增加复活次数；
- 写入复活日志；
- 广播 WebSocket 消息；

#### 3）对局结束判断

当有玩家死亡时，后端要区分两种情况：

- **可复活**：先不结束整局，等待玩家完成广告；
- **不可复活**：直接进入结算；

---

### 4.3 建议新增的 WebSocket 消息

#### 广告复活可用

- `match.revive.available`

#### 广告复活成功

- `match.revive.success`

#### 广告复活失败

- `match.revive.failed`

这样前端可以实时刷新状态。

---

## 5. 前端需要做什么

### 5.1 在对局界面增加复活入口

当玩家血量为 0 时：

- 显示“观看视频广告复活”按钮；
- 显示剩余复活次数；
- 显示当前是否还能复活；

### 5.2 广告播放流程

如果当前前端只是把视频文件放在静态资源目录里，本地联调时可以直接用 `<video>` 播放，不一定要接广告 SDK。

前端需要：

1. 先判断当前玩家是否可复活；
2. 在对局页中显示一个视频播放弹窗或独立区域；
3. 播放静态资源目录中的广告视频；
4. 监听视频 `ended` 事件，确认进度播放完成；
5. 播放完成后，带上 `adRequestId` 调用后端复活接口；
6. 刷新对局状态；
7. 根据后端返回结果更新 UI 和提示；

### 5.3 UI 状态建议

前端最好有以下状态：

- `DEAD_WAIT_RELIVE`：死亡待复活；
- `AD_WATCHING`：视频播放中；
- `REVIVE_SUCCESS`：复活成功；
- `REVIVE_FAILED`：复活失败；

---

## 6. 需要注意的限制

### 6.1 防止无限复活

建议至少加一种限制：

- 每局最多 1 次；
- 或每局最多 2 次；
- 或每个玩家每天最多 N 次；

### 6.2 防止前端伪造“已看广告”

如果只是把视频放在静态资源目录里，本地联调阶段可以直接信任前端的 `ended` 事件。

但为了避免用户手动跳过或伪造完成，建议后端至少：

- 校验 `adRequestId` 是否唯一；
- 记录广告播放开始和结束时间；
- 必要时对视频资源做一次播放完成确认；
- 生产环境再切换到真实广告 SDK 或平台回调；

### 6.3 对局平衡

广告复活会显著改变平衡，建议：

- 只能回 1 点血；
- 复活后有短暂惩罚；
- 或复活后本回合不能行动；

---

## 7. 推荐的最小可落地版本

如果你想快速上线，建议先做最小版：

### 后端
- 给 `match_players` 加 `revive_count`、`last_revive_at`、`revive_status`；
- 新增 `POST /api/matches/{matchId}/revive/request`；
- 新增 `GET /api/matches/{matchId}/revive/status`；
- 增加 `match_revive_logs` 记录表；
- 玩家死亡时先不立即结束，允许一次复活；

### 前端
- 对局页里显示“看视频复活”按钮；
- 死亡时弹出视频播放弹窗或独立区域；
- 视频资源可以放在前端静态目录或后端静态目录；
- 视频播放完成后调用复活接口；
- 刷新对局状态；
- 展示复活次数和倒计时（如果后端提供）；

---

## 8. 推荐的长期方案

如果后面你还要做更多商业化内容，建议增加：

- 广告日志表；
- 每日复活次数限制表；
- 用户广告行为记录表；
- 复活奖励策略配置表；

这样以后方便扩展到：

- 看广告换金币；
- 看广告换道具；
- 看广告换额外回合；

---

## 9. 总结

这个功能最合理的做法是：

- **后端负责判定和落库；**
- **前端负责展示按钮和触发广告；**
- **广告完成后再调用后端复活接口；**
- **复活记录建议落到 `match_players`，必要时再加日志表；**

如果你只想快速实现，先做“每局一次、复活 1 点血”的最小方案最稳妥。
