# 前端对接房间到战斗与结算流程说明

## 1. 当前后端已支持的流程

当前项目从房间创建到正式对局与结算，后端已经支持以下链路：

1. 房间创建与进入；
2. 部门选择；
3. 双方准备；
4. 创建正式对局并发放初始手牌；
5. 选择先手；
6. 正式出牌；
7. 结束回合；
8. 对局结算；
9. 主动放弃；
10. 断线重连与等待重连。

---

## 2. 推荐前端对接顺序

### 2.1 房间页

前端当前已对接到房间创建后，建议继续按以下顺序推进：

1. 房间详情轮询或 WebSocket 刷新；
2. 双方都选择部门；
3. 双方都点击准备；
4. 第二名玩家准备成功后，响应中会带回 `matchId`；
5. 同时双方 WebSocket 会收到 `match.started`；
6. 前端据 `matchId` 跳转到战斗页。

---

## 3. 从房间跳转到战斗页

### 3.1 触发条件

满足以下任一条件即可跳转：

- 房间准备接口响应中的房间数据里 `matchId != null`；
- 收到 WebSocket 消息 `match.started`；

### 3.2 跳转后第一步

进入战斗页后，前端应立即调用：

- `GET /api/matches/{matchId}`
- `GET /api/matches/{matchId}/deck`

用于获取：

- 当前对局状态；
- 己方手牌；
- 己方牌库；
- 双方基础血量、护盾、行动点；
- 当前阶段是否为先手选择。

---

## 4. 选择先手阶段

### 4.1 当前规则

当前后端实现为：

- 双方都进入对局并看到手牌后；
- 房主调用先手选择接口；
- 后端确认先手后，把对局阶段切换为 `PLAYER_ACTION`；
- 双方收到 `match.first_player.chosen`。

### 4.2 对接接口

- `POST /api/matches/{matchId}/choose-first-player`

请求体：

```json
{
  "firstPlayerUserId": 3
}
```

### 4.3 前端处理建议

1. 战斗页初始化后先检查 `GET /api/matches/{matchId}` 返回的 `phase`；
2. 如果 `phase = SELECT_FIRST_PLAYER`，展示“选择先手”界面；
3. 如果当前用户是房主，则允许选择；
4. 选择成功后进入 `PLAYER_ACTION`；
5. 若不是房主，则等待 WebSocket 消息 `match.first_player.chosen`。

---

## 5. 正式对局阶段

### 5.1 查询对局状态

接口：

- `GET /api/matches/{matchId}`

前端应展示：

- 双方玩家状态；
- 当前血量；
- 当前护盾；
- 当前行动点；
- 当前阶段 `phase`；
- 当前回合 `currentRound`；
- 己方手牌；
- 对局版本号 `version`；
- `waitingReconnect`：当前是否处于等待重连；
- `reconnectRemainingSeconds`：当前剩余重连秒数。

### 5.3 等待重连时的返回特征

如果有一名玩家断线，前端再次调用 `GET /api/matches/{matchId}` 时，建议重点看：

- `phase = RECONNECT_WAIT`
- `waitingReconnect = true`
- `reconnectRemainingSeconds > 0`
- 断线方的 `players[].playerStatus = RECONNECTING`

示例：

```json

  "code": 200,
```

### 5.4 获取己方完整牌组

接口：

- `GET /api/matches/{matchId}/deck`

可用于展示：

- 手牌列表；
- 牌库剩余数量；
- 弃牌堆数量；
- 调试时查看全卡信息。

## 6. 出牌与结束回合

### 6.1 出牌

接口：

- `POST /api/matches/{matchId}/actions/play-card`

前端应在每次出牌前带上：

- 当前 `version`
- `clientActionId`
- 选中的卡牌实例 ID
- 目标用户（若有）

### 6.2 结束回合

接口：

- `POST /api/matches/{matchId}/actions/end-turn`

前端每次结束回合后：

1. 更新界面中的 `endedTurn`；
2. 等待 WebSocket 通知：
   - `player.turn.ended`
   - `boss.attack.resolved`
   - `round.started`
   - `match.ended`
3. 或再次调用 `GET /api/matches/{matchId}` 拉取权威状态。

---

## 7. 对局结算

### 7.1 触发时机

以下情况会进入结算：

- 正常胜利；
- 正常失败；
- 主动放弃；
- 断线超时收尾；

### 7.2 对接接口

- `GET /api/matches/{matchId}/settlement`

前端进入结算页后应展示：

- `winnerType`
- `victory`
- `totalRounds`
- `durationSeconds`
- `bossRemainingHp`
- 每名玩家的：
  - `resultType`
  - `remainingHp`
  - `damageDealt`
  - `damageTaken`
  - `healingDone`
  - `shieldGranted`
  - `cardsPlayed`
  - `actionPointsUsed`
  - `expAwarded`
  - `moneyAwarded`

---

## 8. 主动放弃对局

接口：

- `POST /api/matches/{matchId}/abandon`

前端建议：

1. 在战斗页提供“放弃对局”按钮；
2. 用户确认后调用该接口；
3. 成功后等待 `match.ended`，然后进入结算页。

---

## 9. 断线重连

### 9.1 当前后端行为

- 一方断开连接后，后端会将该玩家标记为 `RECONNECTING`；
- 对局阶段切换为 `RECONNECT_WAIT`；
- 对手会收到 `match.reconnecting`；
- 默认重连窗口：**60 秒**；
- 重连成功后，后端恢复为 `ACTIVE`，并广播 `match.recovered`；
- 超过 60 秒仍未恢复，系统会按超时失败收尾。

### 9.2 前端展示建议

#### 离线玩家再次登录

登录成功后，如果本地还有 `matchId`，前端应：

1. 调用 `GET /api/matches/{matchId}`；
2. 若 `phase = RECONNECT_WAIT`、`waitingReconnect = true` 或玩家状态为 `RECONNECTING`，展示“是否重连当前对局”；
3. 同时根据 `reconnectRemainingSeconds` 显示倒计时；
4. 调用 `POST /api/matches/{matchId}/reconnect`；
4. 成功后恢复战斗页。

#### 未断线玩家

如果收到 `match.reconnecting`：

- 战斗页展示“等待队友重连”；
- 同时使用 `reconnectRemainingSeconds` 显示倒计时（默认 60 秒）；
- 若收到 `match.recovered`，恢复正常对局；
- 若收到 `match.ended`，直接进入结算页。

---

## 10. WebSocket 事件建议处理

前端战斗页至少处理以下消息：

- `match.started`
- `match.first_player.chosen`
- `card.played`
- `player.turn.ended`
- `boss.attack.resolved`
- `round.started`
- `match.reconnecting`
- `match.recovered`
- `match.ended`
- `room.closed`

原则：

- WebSocket 负责通知；
- HTTP 查询结果负责最终权威状态。

---

## 11. 推荐前端页面状态机

### 11.1 房间页

- `WAIT_ROOM`
- `SELECT_DEPARTMENT`
- `READY_WAIT`

### 11.2 战斗页

- `SELECT_FIRST_PLAYER`
- `PLAYER_ACTION`
- `RECONNECT_WAIT`
- `SETTLEMENT`

### 11.3 结算页

- 展示战斗结果
- 返回大厅
- 清理本地 matchId / roomId 缓存

---

## 12. 前端联调建议

建议按以下顺序联调：

1. 房间创建 -> 部门选择 -> 双方准备；
2. 跳转战斗页并拉取 `GET /api/matches/{matchId}`；
3. 选择先手；
4. 出牌与结束回合；
5. 正常结算；
6. 主动放弃；
7. 断线重连；
8. 超时收尾。

---

## 13. 总结

当前后端已经支持从房间到战斗页、再到结算页的主链路。前端下一步的重点是：

1. 正确处理 `matchId` 跳转；
2. 对接先手选择；
3. 对接战斗状态刷新；
4. 对接断线等待重连；
5. 对接结算页。

建议所有页面都以 `GET /api/matches/{matchId}` 为权威数据源，WebSocket 只负责触发刷新和用户提示。
