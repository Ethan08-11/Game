# 好友在线与游戏状态系统实现及测试说明

## 1. 修改目标

好友列表现在区分“是否在线”和“在线时正在做什么”，统一提供四种业务状态：

```text
OFFLINE  离线
IDLE     在线空闲
IN_ROOM  组队中
IN_MATCH 游戏中
```

只有 `IDLE` 状态允许发送组队邀请。

## 2. 好友接口返回变化

原接口不变：

```text
GET /api/friends
```

每个好友新增：

```json
{
  "onlineStatus": 1,
  "presenceStatus": "IN_ROOM",
  "invitable": false
}
```

字段含义：

- `onlineStatus`：`1` 在线，`0` 离线；
- `presenceStatus`：`OFFLINE/IDLE/IN_ROOM/IN_MATCH`；
- `invitable`：是否允许显示并使用邀请按钮，只有 `IDLE` 为 `true`。

前端推荐显示：

- `OFFLINE`：离线，隐藏或禁用邀请按钮；
- `IDLE`：在线，显示邀请按钮；
- `IN_ROOM`：组队中，禁用邀请按钮；
- `IN_MATCH`：游戏中，禁用邀请按钮。

## 3. 状态计算规则

状态由统一的 `UserPresenceService` 动态计算，好友列表与邀请接口使用完全相同的规则：

1. Redis 中不存在有效 WebSocket Presence 连接时返回 `OFFLINE`；
2. 用户存在未离开的有效房间成员记录，房间绑定的正式对局真实存在，并且该对局 `status=1`、`ended_at IS NULL`、`phase!='FINISHED'`，返回 `IN_MATCH`；
3. 用户存在未离开的有效房间成员记录，并且房间 `status=0/1`，返回 `IN_ROOM`；
4. 其他在线用户返回 `IDLE`。

有效房间还必须满足：

```text
room_members.left_at IS NULL
game_rooms.closed_at IS NULL
game_rooms.status < 3
```

`match_id` 非空不再单独代表正在游戏。历史房间即使保留 `match_id`，只要对应 `matches` 已结束，就不会被识别为 `IN_MATCH`。

状态优先级为：

```text
OFFLINE > IN_MATCH > IN_ROOM > IDLE
```

不在 `users` 表中保存容易过期的状态字段；WebSocket Presence、房间数据和真实对局状态是权威来源。

## 4. 邀请校验

以下接口都调用统一状态服务：

```text
POST /api/rooms/invites
POST /api/rooms/invites/{inviteId}/accept
```

错误提示：

- `OFFLINE`：用户不在线；
- `IN_ROOM`：用户已在房间中；
- `IN_MATCH`：用户正在对局中。

接受邀请时仍然保留双方用户 Redis 分布式锁和二次校验，避免一个用户并发加入两个房间。

## 5. 实时状态通知

好友状态变化消息格式：

```json
{
  "type": "friend.presence.changed",
  "data": {
    "userId": 9,
    "onlineStatus": 1,
    "presenceStatus": "IN_ROOM",
    "invitable": false
  }
}
```

当前已接入的广播时机：

- 双方接受邀请并创建房间后：广播 `IN_ROOM`；
- 双方准备完成并创建正式对局后：广播 `IN_MATCH`。

消息发送给状态发生变化用户的所有好友。前端收到后可以直接更新对应好友，也可以重新调用 `GET /api/friends` 获取权威列表。

对局结束服务已经接入正式战斗流程，以下路径都会进入统一的 `finishMatch()`：

- 玩家出牌将霸凌者血量降至 0；
- 霸凌者攻击导致玩家死亡；
- 下一回合开始时延迟伤害将霸凌者血量降至 0。

统一结束流程会同步更新：

```text
matches.status = 2
matches.phase = FINISHED
matches.ended_at = 当前时间

game_rooms.status = 3
game_rooms.closed_at = 当前时间
game_rooms.player_count = 0

room_members.left_at = 当前时间
room_members.online_status = 0
room_members.ready_status = 0
```

战斗结束后会发送 `match.ended`，相关结束路径也会重新广播玩家 Presence。数据库提交后的可靠事件补偿与广播重试仍属于后续可靠性建设范围。

## 6. 测试准备

准备三个互为好友的用户，例如：

```text
用户3
用户9
用户10
```

分别登录并取得 `accessToken`，再让需要观察消息的用户连接：

```text
ws://localhost:8080/ws/room?accessToken={accessToken}
```

每个页面应先收到 `ws.connected`。用户登录本身不代表 Presence 在线，必须存在有效 WebSocket 心跳连接。

旧测试房间如果已废弃，应设置：

```sql
UPDATE game_rooms
SET status = 3, closed_at = NOW()
WHERE id = 旧房间ID;

UPDATE room_members
SET left_at = NOW()
WHERE room_id = 旧房间ID AND left_at IS NULL;
```

否则旧房间会按设计被识别为有效占用。

## 7. HTTP 状态测试

### 7.1 测试离线状态

1. 确保好友没有有效在线状态；
2. 当前用户调用 `GET /api/friends`；
3. 预期好友字段为：

```json
{
  "onlineStatus": 0,
  "presenceStatus": "OFFLINE",
  "invitable": false
}
```

### 7.2 测试在线空闲

1. 好友登录；
2. 确保好友没有处于有效房间；
3. 调用 `GET /api/friends`；
4. 预期：

```json
{
  "onlineStatus": 1,
  "presenceStatus": "IDLE",
  "invitable": true
}
```

### 7.3 测试组队中

1. 用户3和用户9接受邀请创建房间；
2. 房间应处于 `status=1`，尚无 `matchId`；
3. 使用用户10调用好友列表；
4. 预期用户3和用户9显示：

```json
{
  "presenceStatus": "IN_ROOM",
  "invitable": false
}
```

### 7.4 测试游戏中

1. 用户3和用户9分别选择不同部门并准备；
2. 正式对局创建后，房间应为 `status=2` 且 `matchId` 非空；
3. 使用用户10查询好友列表；
4. 预期两名玩家显示：

```json
{
  "presenceStatus": "IN_MATCH",
  "invitable": false
}
```

### 7.5 测试邀请权威校验

1. 用户3处于 `IN_ROOM` 或 `IN_MATCH`；
2. 用户3尝试邀请用户10，预期失败；
3. 用户10尝试邀请用户3，预期失败；
4. 确认失败请求没有新增 `room_invites`。

## 8. WebSocket 广播测试

### 8.1 房间创建广播

1. 用户10连接 WebSocket，且用户10是用户3或用户9的好友；
2. 用户3和用户9接受邀请创建房间；
3. 用户10应收到对应玩家的 `friend.presence.changed`；
4. `presenceStatus` 应为 `IN_ROOM`，`invitable=false`。

如果用户10同时是双方好友，应收到两条消息，每条 `userId` 不同。

### 8.2 对局开始广播

1. 保持用户10 WebSocket 连接；
2. 用户3和用户9完成部门选择和双方准备；
3. 创建正式对局后，用户10应收到状态变化消息；
4. `presenceStatus` 应为 `IN_MATCH`。

### 8.3 HTTP 兜底验证

WebSocket 是状态变化通知，不是唯一权威来源。如果消息丢失，前端重新请求：

```text
GET /api/friends
```

返回状态应与数据库中的当前房间和对局状态一致。

## 9. WebSocket 心跳与 Redis 在线状态

在线状态已经不再使用“Token 是否过期”判断。Token 只在 WebSocket 建立连接时用于认证用户身份。

连接地址改为：

```text
ws://localhost:8080/ws/room?accessToken={accessToken}
```

不再接受前端直接传入 `userId` 作为身份，因为用户 ID 可以伪造。

连接建立后服务端返回：

```json
{
  "type": "ws.connected",
  "message": "connected",
  "heartbeatIntervalSeconds": 20,
  "onlineTimeoutSeconds": 60
}
```

客户端每 20 秒发送：

```json
{
  "type": "ws.heartbeat",
  "timestamp": 1784809466007
}
```

服务端响应：

```json
{
  "type": "ws.heartbeat.ack",
  "timestamp": 1784809466007
}
```

Redis 使用：

```text
ZSet: wa:demo:presence:connections
member: userId:connectionId
score: 最后心跳毫秒时间戳

String: wa:demo:presence:user:{userId}:{connectionId}
TTL: 60秒
```

同一用户每个窗口或客户端拥有独立 `connectionId`。只要任意一个连接的心跳 Key 仍存在，用户就保持在线；关闭其中一个窗口不会影响其他连接。

### 9.1 心跳测试

1. 登录并复制 `accessToken`；
2. 打开更新后的 `WebSocketRoomTest.html`；
3. 输入 Token 并连接；
4. 确认收到 `ws.connected`；
5. 等待 20 秒，确认持续收到 `ws.heartbeat.ack`；
6. 使用好友账号调用 `GET /api/friends`，应显示该用户在线；
7. 关闭测试页，好友列表刷新后应显示离线；
8. 如果连接异常未触发关闭回调，停止心跳 60 秒后应自动判定离线。

### 9.2 多窗口测试

1. 使用同一用户 Token 打开两个测试页；
2. 两个页面都连接并保持心跳；
3. 关闭其中一个页面；
4. 好友列表仍应显示该用户在线；
5. 再关闭第二个页面，用户才变为离线。

### 9.3 Token 认证测试

1. 不传 `accessToken` 连接，预期 WebSocket 被关闭；
2. 使用无效或过期 Token 连接，预期关闭码为策略违规；
3. 使用有效 Token 连接，身份由 Token 解析，不允许客户端指定其他 `userId`。

### 9.4 前端刷新建议

- 心跳间隔：20 秒；
- 在线超时：60 秒；
- 好友列表兜底刷新：30 秒；
- 收到 `friend.presence.changed` 时立即局部更新或重新拉取好友列表。

## 10. 当前已实现的房间与对局生命周期

### 10.1 接受邀请后立即创建房间

接受邀请成功后，后端会在事务中立即：

```text
创建 game_rooms
插入双方 room_members
房间 player_count=2
房间 status=1
邀请 status=1 并绑定 room_id
广播 room.invite.accepted 与 room.created
广播双方 friend.presence.changed=IN_ROOM
```

数据库房间创建不依赖前端页面是否成功跳转。即使前端跳转失败，房间仍已正式成立，双方再次查询好友列表时会显示 `IN_ROOM`。

### 10.2 接受邀请时的并发和状态校验

接受邀请会按用户 ID 固定顺序获取双方 Redis 分布式锁，并在事务内重新校验：

- 邀请接收人；
- 邀请是否已处理；
- 邀请是否过期；
- 双方好友关系；
- 双方实时 Presence 是否为 `IDLE`。

这可以避免同一用户并发接受多个邀请后同时加入两个新房间。

### 10.3 历史成员记录清理

接受邀请前会调用历史成员清理。对于 `left_at IS NULL`，但对应房间已经满足以下任一条件的记录：

```text
房间不存在
closed_at IS NOT NULL
status IS NULL
status >= 3
```

后端会将该成员记录更新为：

```text
left_at = 当前时间
online_status = 0
```

此清理只处理已经可以明确判断为失效的房间，不会自动删除仍为 `status=0/1/2` 的房间，避免误伤真实活跃房间。

### 10.4 正式对局结束清理

对局正常结束时会统一关闭对局、房间和成员关系。完成后，如果用户 WebSocket 仍在线且没有其他有效房间，其 Presence 应变为 `IDLE`；如果所有 WebSocket 连接均失效，则为 `OFFLINE`。

### 10.5 未开始房间主动退出机制

当前已经提供：

```text
POST /api/rooms/{roomId}/leave
```

任意房间成员可在正式对局开始前调用。双人房间中一方退出会关闭整个房间、将双方成员标记为离开、发送 `room.closed`，并广播双方最新 Presence。已经绑定正式对局或 `status=2` 的房间拒绝普通退出。

关闭页面或客户端本身仍只会解绑 WebSocket 连接并在 60 秒内更新在线状态，不会自动执行：

```text
game_rooms.status = 3
game_rooms.closed_at = 当前时间
room_members.left_at = 当前时间
```

因此，接受邀请后如果前端页面跳转失败、用户关闭客户端或网络中断，而房间又尚未开始正式对局，数据库中的 `status=1` 房间会继续保留。用户重新上线后仍可能被判断为 `IN_ROOM`，并因 `invitable=false` 无法创建新邀请。

不能在 WebSocket 短暂断开时立即关闭房间，因为页面刷新、网络抖动以及同一用户多窗口都会产生正常的临时断线。后续需要结合退出接口、重连恢复和超时回收机制解决。

### 10.6 当前未开始房间的恢复边界

当前没有独立的“查询当前活跃房间”恢复接口。前端应保留接受邀请响应或 `room.created` 中的 `roomId`，并在跳转失败后调用房间详情接口恢复。如果客户端彻底丢失 `roomId`，现阶段缺少完整的后端恢复入口。

## 11. 对局结束后的状态测试

### 11.1 玩家胜利

1. 让玩家立即伤害或延迟伤害将霸凌者血量降到 0；
2. 检查 `matches.status=2`、`phase=FINISHED`、`ended_at` 非空；
3. 检查 `game_rooms.status=3`、`closed_at` 非空、`player_count=0`；
4. 检查该房间双方 `room_members.left_at` 非空；
5. 保持玩家 WebSocket 在线，使用好友账号调用 `GET /api/friends`；
6. 预期玩家状态为 `IDLE`、`invitable=true`。

### 11.2 玩家失败

1. 双方结束回合，让霸凌者攻击导致任一玩家死亡；
2. 检查对局、房间和成员关系与 11.1 相同；
3. 确认好友列表不再返回 `IN_MATCH` 或 `IN_ROOM`。

### 11.3 历史 `match_id` 不误判

1. 保留已关闭房间中的历史 `match_id`；
2. 确认对应 `matches.status=2` 或 `phase=FINISHED`；
3. 好友列表不应仅因 `match_id` 非空返回 `IN_MATCH`。

## 12. 当前边界汇总

- 在线状态由 WebSocket 心跳和 Redis Presence 连接记录判断；
- `IN_MATCH` 必须由真实未结束的 `matches` 记录确认；
- 正式对局结束时已同步关闭对局、房间和成员关系；
- 接受邀请前会清理明确失效的历史成员记录；
- 当前没有新增数据库字段或迁移脚本；
- WebSocket 测试页使用 Token 认证并自动每 20 秒发送心跳；
- 未开始房间已有主动退出接口，但尚无断线宽限期回收和定时超时关闭；
- 页面跳转失败不会撤销已经成功创建的数据库房间；
- 数据库仍为 `status=0/1/2` 的旧房间不会被自动当作过期数据清理；
- WebSocket 广播尚未具备持久化重试和可靠事件补偿。
