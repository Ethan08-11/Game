# 作战与出牌逻辑说明

本文档整理当前项目中“从组队进入对局、选择先手、出牌、结束回合、结算”的完整逻辑，方便联调、排查和后续迭代。

---

## 1. 总体流程

完整作战流程如下：

1. 双方成功组队；
2. 双方选择部门；
3. 双方点击准备；
4. 后端创建正式对局 `matchId`；
5. 前端进入 `/battle/:matchId`；
6. 前端查询对局权威状态；
7. 房主选择先手；
8. 双方正式出牌；
9. 当前玩家结束回合；
10. 双方都结束后，霸凌者行动；
11. 进入下一回合或直接结算；
12. 对局结束后进入结算页。

---

## 2. 组队进入作战

### 2.1 关键接口

第二名玩家准备成功后，前端调用：

```http
POST /api/rooms/{roomId}/ready
```

后端会：

- 校验玩家是否已选择部门；
- 更新 `room_members.ready_status`；
- 判断当前房间是否两人都已准备；
- 若满足条件，则创建正式对局；
- 返回最新房间信息，通常会包含 `matchId`；
- 同时可能推送 WebSocket 消息。

### 2.2 前端进入对局的触发点

当前前端对进入对局做了多路兜底：

- `ready` 接口返回里有 `matchId`，立即进入对局；
- WebSocket 收到 `match.started`，立即进入对局；
- 房间详情同步里发现 `matchId`，立即进入对局；
- 本地缓存 `room.matchId` 或 `localStorage.activeMatchId` 也可兜底。

最终都会跳转到：

```text
/battle/:matchId
```

---

## 3. 战斗页初始化

战斗页路由为：

```text
/battle/:matchId?
```

### 3.1 进入页面时的初始化顺序

战斗页挂载后会：

1. 读取 `route.params.matchId`；
2. 若没有，再尝试 `room.matchId`；
3. 再尝试 `localStorage.activeMatchId`；
4. 如果仍然没有 `matchId`，则回到组队页；
5. 有 `matchId` 后，调用重连接口；
6. 再调用对局详情接口，恢复当前权威状态；
7. 订阅对局相关 WebSocket 事件。

### 3.2 重连接口

```http
POST /api/matches/{matchId}/reconnect
```

作用：

- 恢复短暂断线后的对局状态；
- 让前端重新同步当前回合、手牌、血量、阶段等信息。

### 3.3 权威查询接口

```http
GET /api/matches/{matchId}
```

这是战斗页最重要的权威状态来源。

通常会返回：

- `phase`
- `currentRound`
- `version`
- `firstPlayerUserId`
- `firstPlayerChosenByUserId`
- `players[]`
- `hand[]`
- `bossCurrentHp`
- `bossCurrentAttack`
- `customer`
- `matchEnded`
- `winnerType`

---

## 4. 选择先手

### 4.1 进入先手阶段

如果当前对局阶段是：

```text
SELECT_FIRST_PLAYER
```

则前端会进入先手选择流程。

### 4.2 选择先手接口

```http
POST /api/matches/{matchId}/choose-first-player
```

请求体示例：

```json
{
  "firstPlayerUserId": 3
}
```

### 4.3 成功后效果

后端会：

- 记录本回合先手玩家；
- 将阶段切换到 `PLAYER_ACTION`；
- 通知双方先手选择结果；
- 前端继续进入出牌阶段。

---

## 5. 出牌逻辑

### 5.1 手牌来源

当前前端只展示**当前登录用户自己的手牌**。

手牌来自：

```http
GET /api/matches/{matchId}
```

接口返回中的：

```json
"hand": []
```

每张牌都使用本局实例 `instanceId`，而不是模板 `cardId`。

### 5.2 出牌接口

```http
POST /api/matches/{matchId}/actions/play-card
```

请求体示例：

```json
{
  "cardInstanceId": 1,
  "targetType": "BOSS",
  "targetUserId": null,
  "clientActionId": "user9-round1-action1",
  "expectedVersion": 1
}
```

### 5.3 请求字段说明

- `cardInstanceId`
  - 本局卡牌实例 ID，来自 `hand[].instanceId`；
  - 不是卡牌模板 ID。

- `targetType`
  - `BOSS`：攻击霸凌者；
  - `PLAYER`：作用于玩家。

- `targetUserId`
  - 目标玩家 ID；
  - 攻击霸凌者时必须为 `null`。

- `clientActionId`
  - 客户端生成的本次操作唯一编号；
  - 用于防重复提交。

- `expectedVersion`
  - 客户端认为当前对局版本号；
  - 必须与服务器一致，否则会被拒绝。

### 5.4 后端校验

出牌时后端会检查：

- 卡牌是否属于当前玩家手牌；
- 版本是否匹配；
- 操作编号是否重复；
- 是否满足部门条件；
- 目标类型是否正确；
- 当前行动点是否足够。

### 5.5 出牌响应

成功后会返回：

- `actionId`
- `cardInstanceId`
- `effectType`
- `effectValue`
- `remainingActionPoints`
- `version`
- `matchEnded`
- `winnerType`
- `effects[]`

其中 `effects[]` 是结构化效果数组，表示这张牌本次实际触发了哪些效果。

---

## 6. 结构化卡牌效果

当前出牌已经不是简单的数值字段，而是结构化效果。

### 6.1 常见效果类型

- `DAMAGE_BOSS`
- `HEAL_PLAYER`
- `ADD_SHIELD`
- `ADD_ACTION_POINTS`
- `MULTIPLY_NEXT_CARD`

### 6.2 触发时机

- `IMMEDIATE`
  - 立即执行；

- `ROUND_START`
  - 下一回合开始时执行；

- `NEXT_CARD`
  - 下一张牌翻倍或附加效果。

### 6.3 效果结果字段

每条效果通常包含：

- `effectType`
- `triggerTiming`
- `targetType`
- `targetUserId`
- `baseValue`
- `actualValue`
- `beforeValue`
- `afterValue`
- `scheduled`
- `triggerRound`
- `pendingEffectId`

---

## 7. 员工调用机会

前端里展示为“员工调用机会”，后端字段一般对应：

- `actionPoints`

### 7.1 基本规则

- 每打出一张牌会消耗对应行动点；
- 部分牌会额外增加行动点；
- 下一回合行动点会重置；
- 战斗页以对局权威状态为准，不使用纯前端本地猜测。

---

## 8. 结束回合逻辑

### 8.1 结束回合接口

```http
POST /api/matches/{matchId}/actions/end-turn
```

请求体示例：

```json
{
  "clientActionId": "user9-round1-end",
  "expectedVersion": 3
}
```

### 8.2 结束回合时发生什么

后端会：

1. 将当前玩家本回合剩余手牌进入弃牌堆；
2. 标记该玩家已结束回合；
3. 如果还有玩家没结束，等待对方结束；
4. 如果双方都结束，则霸凌者行动；
5. 如果双方都存活，则进入下一回合；
6. 如果有人死亡，则直接结束对局。

### 8.3 结束回合响应中常见字段

- `endedTurn`
- `discardedCount`
- `allPlayersEnded`
- `bossAttackResolved`
- `resolvedRound`
- `bossAttackTargets`
- `matchEnded`
- `winnerType`
- `currentRound`
- `phase`
- `version`
- `handCount`
- `deckCount`
- `discardCount`

---

## 9. 霸凌者攻击与下一回合

当双方都结束后，后端会触发霸凌者攻击。

### 9.1 `bossAttackTargets`

这个数组会描述双方受到的伤害明细，例如：

- 被谁攻击；
- 伤害是多少；
- 护盾吸收了多少；
- 实际扣了多少血；
- 是否死亡。

### 9.2 进入下一回合

如果双方都存活，则：

- `currentRound + 1`
- `actionPoints` 重置
- 重新抽牌
- `phase` 回到 `PLAYER_ACTION`

### 9.3 对局结束

如果出现以下情况，则对局结束：

- 霸凌者血量归零；
- 某一方玩家死亡；
- 主动放弃；
- 掉线超时判负。

结束后：

- `matchEnded=true`
- `winnerType` 返回对应胜负类型
- `phase=FINISHED`

---

## 10. WebSocket 在作战中的作用

WebSocket 只负责通知，不负责最终裁决。

### 10.1 会监听的事件

- `match.started`
- `match.first_player.chosen`
- `card.played`
- `player.turn.ended`
- `boss.attack.resolved`
- `round.started`
- `match.ended`
- `match.reconnecting`
- `match.recovered`

### 10.2 处理方式

收到 WebSocket 事件后，前端通常会：

1. 先记录事件中的 `matchId`；
2. 再调用 `GET /api/matches/{matchId}`；
3. 用 HTTP 权威状态刷新页面。

---

## 11. 结果页与离开对局

### 11.1 结算页

对局结束后会进入结果页：

```text
/result/:matchId
```

### 11.2 主动离开对局

如果玩家主动放弃，前端会调用：

```http
POST /api/matches/{matchId}/abandon
```

然后：

- 清理本地 `activeMatchId`；
- 清理房间状态；
- 回到大厅。

---

## 12. 复盘一下完整调用顺序

```text
组队成功
→ 选择部门
→ 点击准备
→ ready 接口返回 matchId
→ 前端进入 /battle/:matchId
→ reconnectMatch
→ GET /api/matches/{matchId}
→ 选择先手
→ 出牌
→ 结束回合
→ 霸凌者攻击
→ 下一回合 or 直接结算
→ /result/:matchId
```

---

## 13. 排查作战问题时的优先顺序

如果作战进不去，按下面顺序查：

1. `POST /api/rooms/{roomId}/ready` 是否返回 `matchId`；
2. 前端是否真的跳到了 `/battle/:matchId`；
3. 战斗页是否成功拿到 `route.params.matchId`；
4. `POST /api/matches/{matchId}/reconnect` 是否成功；
5. `GET /api/matches/{matchId}` 是否返回权威状态；
6. 是否被全局 WebSocket 事件推回了别的页面；
7. 是否有运行时导入错误导致战斗页组件加载失败。

---

## 14. 结论

当前项目的作战逻辑核心是：

- **房间准备接口负责产出 `matchId`**；
- **前端以 `matchId` 进入战斗页**；
- **战斗页以 `GET /api/matches/{matchId}` 为权威状态源**；
- **出牌与结束回合都必须带 `expectedVersion`**；
- **WebSocket 只做同步通知，不做最终裁判**。

如果后续再出现“状态已进入游戏，但页面没进入作战”，优先检查：

1. `matchId` 是否稳定传到 `/battle/:matchId`；
2. 战斗页是否有运行时导入错误；
3. 全局 WebSocket 事件是否又把路由改回去了。
